# 確認済みの制約

自動化時に取り違えやすい条件をまとめる。対象ケースに関係する項目だけを適用し、無関係な条件を新たな実行前提にしない。

## 共通の確認原則

- 画面、DB、ログ、通信応答はそれぞれ別の観測。必要な観測ができない場合は未確認部分を明記し、他の成功から補完しない。
- 登録アカウント、権限、環境設定の実値は登録環境で確認する。秘密値は知識庫・結果報告に転記しない。

## 受付アプリの注意点

| 項目 | 判断に使う規則 |
| --- | --- |
| 起動引数 | ユーザーコード・ハッシュ・広域フラグ・研修フラグの引数名は `userCd=`・`hash=`・`koikiLoginFlg=`・`trainingFlg=`。業務項目名の `loginId`・`hashInfo`・`globalFlg` をそのまま起動引数名として渡さない |
| 初期画面 | 受電・救援依頼入力・研修用依頼情報コピーはモードレスの独立ウィンドウ。表示有無とモーダル性は別に確認する |
| 入力画面の閉じる操作 | 救援依頼入力画面と子画面の終了／非表示であり、受電画面からの全体ログアウトと同一ではない |
| ユーザー・端末情報 | RSCC 情報は `v_rscc`、装置情報は端末 IP・有効フラグで関連付く。LEFT JOIN のため装置不一致だけでユーザー取得が必ず 0 件になるとは限らない |
| 権限の項目名 | 権限区分コードは `auth_cls_cd`、取得結果の別名は `authClsCd`。ユーザーコードとは区別する |
| 復旧対象 | 復旧画面の対象は先頭の受付番号。受付更新・ロック解除は取得した受付番号リストが対象。 |
| 対象支部が 0 件 | 支部ごとの登録は 0 件となる。「処理が正常終了」と「レコードが作成された」を区別する |

## 受付アプリの環境・観測上の制約

| 制約 | 判断の境界 |
| --- | --- |
| 認証・端末・権限は環境の登録データ依存 | 起動条件には有効ユーザー、端末 IP／番号、所属、内線、権限割当が関係する。具体値は登録環境で照合する |
| CTI 無効化または使用開始異常でも画面が開く場合がある | 画面表示成功と CTI 試験の成立を分ける。 |
| 二重起動は同名プロセス数で検出し、正常ログアウトは CTI の同名プロセス群を終了する | 同じ Windows 環境の別利用と干渉し得る。テスト用利用条件の範囲で操作し、別プロセスを Agent が独断で終了しない |
| 終了処理の異常と画面消失は両立し得る | 終了処理の例外後にもプロセス終了へ進む場合がある。ウィンドウ消失だけで終了ログ・DB 後処理・コミット成功を推定しない |
| UIA 要素列挙上限（300 件）と全角空白・展開ツリー | 救援依頼入力画面（`JAFRSAO02001`）や依頼情報照会画面（`JAFRSAO03002`）では `inspect_window` が 300 要素で打ち切られる（`truncated: true`）ことがある。画面上のボタン・ラベル表記にある全角空白（例：`「開　始」`、`「住　所」`、`「名　称」`）を保持して照合し、試験対象外の展開済みツリー（例：依頼情報照会画面の「エリア」`TreeItem` / `Expander`）が要素枠を消費している場合は一時的に `collapse` して再観測することで後続要素の `automationId` / `elementId` を取得する |
| 同名ノード・親子要素の衝突 | WPF のボタン・チェックボックス等は同名の内部 `Text` 子要素を持つほか、同一画面内に `「参照」`・`「クリア」`・`「◂登録住所」` 等の同名ボタンや無名 `toggleButton` が複数存在する。`name` 単独指定で複数一致（`AMBIGUOUS_ELEMENT`）となる場合は、直ちに定位不能とせず、文脈（対象項目名、`automationId` の業務名、操作可能な親 `controlType`、近傍ラベルとの `boundingRectangle` 位置関係、補助画像）から該当する 1 ノードを選んで操作を試行する |
