# 権限・役割

## 共通の権限照会

共通の権限照会は、`m_gyomu_kengen_wariate_info` のアプリコード・権限区分コード・ロールコードの組合せで許可を確認する。引数不足、該当割当なし、照会処理の例外は権限なし側の戻り値になる。機能の利用可否はロール名だけでは決まらない。

認証方式、権限を確認するタイミング、拒否時の表示・終了動作はアプリ・機能ごとの条件に従う。

## 自動テスト用アカウント

テストアカウントの役割・ユーザー名・パスワードは、FlaUI MCP の対象 app 設定で管理する。ランチャーのログインには LNC 用の登録アカウントを使用する。実値は知識庫へ記載せず、アカウントの選択・入力は MCP が公開する設定参照とログイン操作の契約に従う。未公開の設定キーやツール名を推測しない。

設定上の役割は、ケースに適したアカウントを選ぶための用途・区分であり、業務権限を付与するものではない。実際の利用可否は対象アプリの DB 割当と画面状態で決まる。ユーザー名・パスワードの再入力をタスクの共通必須項目にせず、秘密値をレビュー報告・操作記録へ転記しない。

## 受付アプリの認証と権限取得

1. ランチャーから受け取った起動時のユーザーコード・ハッシュを `t_term_status_info` と照合する。受付画面にパスワードを入力して認証する処理ではない。
2. `v_user_info` から有効期間内のユーザーと `role_cd` を取得し、端末・所属・表示設定を組み合わせる。
3. `m_gyomu_kengen_wariate_info` からそのロールの `appli_cd='UKT'` の権限を取得する。
4. 画面・ボタンごとに個別の権限を確認する。

「認証できた」と「画面・操作が許可された」は別。権限チェック失敗だけでは、割当不足と DB 読取失敗を区別できないため、原因はログ等と照合する。

## 受付アプリの参照状態・業務状態による制御

表示・操作の権限があっても、参照指定や業務状態によって操作が制限される。

| 状態・条件 | 対象 | 制御 |
| --- | --- | --- |
| `IsReadOnly=true` | 依頼区分選択画面 | 選択ボタンを非活性にする |
| `IsReadOnly=true` | ウェブ受付／JAFアプリチャット画面 | 対応ボタンを非活性にする |
| 読み取り専用指定が `ON` | 対話履歴画面 | 指令取消、TS対応結果登録、修正登録、新規登録を非活性にする |
| `UketsukeServerKbn == 3` | 救援依頼入力画面の研修ボタン | A0212の権限に加え、この条件を満たす場合に表示する |

参照指定を受け取った画面は、その値に応じて操作を制御する。どの入力状態で参照指定を渡すかは、呼出し元の処理によって決まる。

開始ボタンは復旧・表示モード等、予約問合せの操作は参照状態・予約条件等の影響も受ける。実際の操作可否は、権限と対象画面の状態を合わせて判断する。

## ロール割当と実行条件

ロール名称・利用者別の許可一覧は DB の割当データに依存する。「管理者」「一般担当者」という名称だけから固定権限表やテスト用アカウントを作らない。研修フラグ・広域フラグを変更して権限を代用しない。対象ケースが権限差を必要とするときだけ、登録済みの利用者と対象権限を照合する。
