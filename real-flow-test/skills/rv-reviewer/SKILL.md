# テスト仕様書レビュー

## 目的と役割

指定されたテスト仕様書（Excel 等）を Markdown に変換し、プロジェクトの業務知識を参照して「テスト手順と期待結果が明確で、矛盾なく検証可能か」をレビューする。変換後の仕様書 Markdown（末尾に適用範囲の付記を追加したもの）を保存し、判定が `FAIL`（要修正）の場合のみ詳細なレビュー報告を作成・保存する。他の Skill の呼び出しやテスト環境での画面操作は行わない。

## リソースの確立と業務知識の参照

1. **入力仕様書と保存先の確立**
   - 実行コンテキストからレビュー対象のテスト仕様書（文書 ID・パス・版情報）と成果物の保存先プレフィックス（指定がなければ `レビュー/`）を確認する。対象が未指定の場合は対象範囲の確認を求め、文書庫全体へ自動的に拡大しない。
   - 文書を参照・記録する際は、文書メタデータが示す文書庫内の論理相対パス（`path` または `folder/name`）を `objectKey` として使用し、物理ストレージキーや作業用の一時ローカルパスで置き換えない。

2. **データベースの自律確認と使い分け**
   - **テスト管理記録（接続されている場合）**：実行環境にテスト管理用のデータベースが提供されている場合は、利用可能なスキーマ・テーブル構造を確認し、今回のレビュー実行（`testRunId`）、対象文書（`documentId`・元仕様書の SHA-256 ハッシュである `specVersion`）、保存した成果物の参照（変換済み `MARKDOWN`・`FAIL` 時の `RV_RESULT`）、およびレビュー判定（`PASS` / `FAIL`）と処理状態（`RUNNING` → `COMPLETED` / `FAILED`）を記録する。データベース側で自動導出される生成列には直接書き込まない。
   - **被測システムの業務データベース（任意・読取専用）**：仕様の理解にあたり被測アプリケーションのテーブル定義やマスターデータの確認が必要な場合のみ、読取専用で参照する。レビュー中に業務データを変更せず、業務データベースが未接続・参照不能であること自体を仕様書の RV 不合格理由にはしない。

3. **業務知識の段階的参照（全件一括読取の禁止）**
   - **開始時の最小読取**：処理開始時は、プロジェクト文書庫にある業務知識の索引（`INDEX.md`）と共通の仕様書表記・改訂規則の文書のみを読み、収録されている知識の全体像と仕様書の書式ルールを把握する。知識庫内の全ファイルを無差別に一括列挙・連続読取しない。
   - **対象仕様書に応じた選択読取**：仕様書を変換して表紙・対象機能・対象画面を確認した上で、`INDEX.md` の一覧から当該仕様書の審査に必要な業務・画面・権限・既知制約の文書だけを選択してオンデマンドで読み取り、同一実行内で再利用する。

## ツールの使用原則

- **公開契約に基づく自律操作**：実行環境が公開するツールの説明と入出力 Schema から利用可能な文書取得・変換・ファイル読取・ストレージ保存・データベース操作の能力を確認し、その契約に従って実行する。
- **大判文書の効率的読取**：変換後の仕様書 Markdown 全文を確認する際は、数十行ずつの細切れ読取を繰り返さず、読取ツールが許容する大きな文字数・行範囲を使って少数の呼び出しで全文と末尾の書式情報を欠落なく読み取る。検索結果や要約だけで全文確認済みにしない。
- **受控書込と反映確認**：ストレージへの成果物保存や管理記録の更新を行う際は、観測・提案・承認・適用・回読の手順を守り、書き込んだ内容と状態が確実に反映されたことを確認する。

## レビューの実行フロー

1. **実行開始の確定と対象文書の取得**
   - 新しいレビュー依頼ごとに一意の `testRunId`（UUID）を発行し、管理記録に実行開始（`RUNNING`）を登録する。
   - 対象仕様書（または明示指定されたディレクトリ内の当日更新仕様書。一時ファイル `~$` や成果物保存先は除外）ごとに `documentId`（UUID）を発行して取得し、元ファイルの SHA-256 ハッシュ（`sha256:<64桁小文字16進数>`）を `specVersion` として記録する。

2. **Markdown への変換と原文・書式の確認**
   - 文書変換ツールを用いて対象仕様書を Markdown に変換し、生成された本文とセル書式情報（背景色・削除線・文字色等）、および内容ハッシュを確認する。
   - 空セルに由来する `NaN` や `Unnamed` などの変換表記を直ちに仕様不備とみなさない。審査に必要な表構造や記述が変換過程で欠落した疑いがある場合は元文書と照合し、変換自体の失敗や情報欠落は「処理異常（`FAILED`）」としてレビュー判定の `FAIL` と区別する。

3. **有効範囲の特定と明確さ・検証可能性の審査**
   - **有効範囲の切り分け**：業務知識の表記・改訂規則に従い、廃止・対象外（灰色背景のセル/行や削除線等）を除いた有効な記述を特定する。部分的な改訂がある場合は、有効な記述と残る前提条件・期待結果を正しく対応付ける。
   - **審査の観点**：有効範囲内の各テストケースについて、対象機能・画面、前提条件、操作手順、入力データ、および期待結果が明確であり、業務知識に照らして互いに矛盾せず検証可能かを確認する。Given / When / Then などの特定の記述形式は強制せず、正常系確認を目的とする仕様書に無関係な異常系ケースの追加を要求しない。
   - **自動化実装詳細の非強制**：UI セレクター、ツール名、接続先設定、テスト用パスワードなどの自動化実行固有の情報が仕様書に書かれていないことを理由に `FAIL` にしない。秘密値を仕様書や報告へ転記させない。
   - **合否基準**：有効範囲のテスト内容を理解・検証できれば `PASS` とする。要求の矛盾、必須の前提・手順・データの欠落、または検証不能な期待結果がある場合は `FAIL` とし、対象箇所（シート・ケース ID・原文引用）、重要度、影響、および具体的な修正案を整理する。

4. **仕様書 Markdown（適用範囲付記付き）の保存**
   - 変換された仕様書 Markdown の原バイト列を一切改変・要約・清書せず保持したまま、末尾に区切り改行と `## RV 確認済みの適用範囲` セクションを追加する（モデルによる全文再出力や別形式への書き換えは行わない）。
   - `## RV 確認済みの適用範囲` には、「RV による付記（仕様原文ではない）」である旨、`testRunId`・`documentId`・`specVersion`、適用した表記規則、除外した箇所、部分改訂で採用した有効範囲、および後続のテスト実行・結果判定が引き継ぐべき業務知識上の前提解釈を簡潔に明記する（全ケースが廃止の場合は有効対象 0 件と記す）。
   - `PASS` / `FAIL` を問わず、この最終版 Markdown を `レビュー/{testRunId}/{documentId}/テスト仕様書.md` として保存し、成果物参照（`MARKDOWN`）を記録する。

5. **レビュー報告の条件付き保存と完了記録**
   - **レビュー報告（`FAIL` 時のみ）**：判定が `FAIL` の場合のみ、仕様書作成者が修正箇所と理由を把握できる日本語 Markdown の `レビュー/{testRunId}/{documentId}/レビュー報告.md` を作成・保存し、成果物参照（`RV_RESULT`）を記録する。報告には結論（文書名・`FAIL` の理由・重要度別件数）、確認範囲、指摘一覧表、指摘別の詳細（原文引用・問題と影響・修正案）、および次工程へ進むための条件と参照情報を含める。`PASS` の場合はレビュー報告を作成しない。
   - **管理記録の確定と完了報告**：対象文書の判定結果（`verdict` および最小 JSON 記録 `{"verdict": "PASS" | "FAIL"}`）と処理完了状態（`COMPLETED`、`finished_at`）を保存・回読し、全対象文書の処理後に実行全体の状態と集計件数を確定させる。同一実行の再開時は登録・保存済みの成果物を再利用して未完了分から継続し、終了時は実行 ID、文書ごとの判定・状態・保存先パスを簡潔に報告する。
