# テスト仕様書レビュー（RV）

## 目的と入力

選択した Excel のテスト仕様書を Markdown に変換し、業務知識を参照してレビューする。変換本文と判定を保存し、`FAIL` の場合だけレビュー報告を作成する。他の Skill は呼び出さず、レビューと成果保存までを扱う。

- **必須入力**：選択された Excel のテスト仕様書（パス・文書 ID・版は選択情報と文書メタデータから取得）。対象が未指定なら範囲の指定を求め、文書庫全体へ自動拡大しない。
- **実行環境と保存先**：接続済みの MinIO、PostgreSQL、MarkItDown を使用する。プロジェクト、文書庫、bucket、タイムゾーン（既定 `Asia/Tokyo`）は実行情報から取得する。成果物保存先は指定がなければ `レビュー/` を使い、明示設定があれば以下の `レビュー/` を置き換える。既存文書・ID・JSON キーは維持し、元仕様は依頼なく変更しない。
- **ツール・外部書込の原則**：実行環境が公開する許可済みツールの説明・入出力 Schema から必要な能力を選び、具体的なツール名・引数・状態・読取上限はその契約に従う（既知製品の API を前提にしない）。外部書込は観測・提案・承認・適用・回読の手順を守り、ツールの説明を権限とみなさない。DB・Schema の項目名は業務保存契約であり、外部 API に同じ名前を要求せず確認した実データを対応付ける。

## データベースの使い分け

- **テスト管理データベース（PostgreSQL、必須）**：`test_automation` の実行・文書・判定・成果物記録を保存する接続。
- **業務データベース（任意）**：仕様の理解に必要な場合だけ、被測アプリの表構造・定義・参照データを読取専用で確認する別接続。レビュー中に業務データを変更したり試験操作を実行したりしない。

同じ製品やサーバーでも用途別に選択し、業務 DB に `test_automation` の存在を求めない。業務 DB の未設定・取得不能だけを RV 不合格や全体の停止理由にせず、判定を左右する未確認事項だけを不足として記録する。

## 業務知識の参照

処理開始時はプロジェクト文書庫の `JAF業務知識/INDEX.md` と `JAF業務知識/共通/仕様書の表記・改訂規則.md` の 2 ファイルのみを読む（`JAF業務知識/` 内の全ファイルを一括列挙・連続読取しない）。変換後の仕様書の表紙・対象機能・画面 ID を確認した上で、`INDEX.md` のルーティング表から対象範囲に該当する用語・権限・業務・画面の文書のみをオンデマンドで取得し、読み取った内容は同一実行内で再利用する。

業務の解釈は知識庫、試験対象・入力・期待結果は仕様書に従い、知識に基づく解釈と対象範囲を末尾の `## RV 確認済みの適用範囲` へ引き継ぐ。

## 処理手順

1. **実行登録**：新しい依頼ごとに `testRunId`（UUID）を生成し、`test_automation.test_run` にプロジェクト、文書庫、bucket、対象パス・抽出条件、タイムゾーン、対象日、抽出基準日時、開始日時、`RUNNING`、成果物保存先（`output_prefix` 列）を登録する。登録失敗時は文書処理を開始しない。
2. **対象選択**：承認された範囲内の `.xlsx` / `.xls` を対象とし、`~$` 一時ファイルと成果物保存先を除外する。個別ファイルと選択時に対象を確定した文書集合は更新日を問わない。実行コンテキストにディレクトリ条件が明示されている場合だけ、`/` 終端の prefix（ルートは空文字）で再帰列挙・全ページ取得し、プロジェクトのタイムゾーン基準で `LastModified` が当日 00:00 以上、翌日 00:00 未満かつ抽出基準日時以前の文書を選ぶ（件数や共通フォルダーから選択方式を推測しない）。
3. **文書登録・変換**：
   - 対象ごとに `documentId`（UUID）を生成して `test_automation.test_document` へ登録し、選択した版の Excel を取得する。Version ID を固定できなければ一覧と取得時のメタデータを照合し、途中で変更された文書は処理異常とする。
   - 取得内容の SHA-256（小文字 16 進数 64 桁）に `sha256:` を付けて `specVersion` とし、更新日時・Version ID・ETag・変換ツールの版を取得可能な範囲で記録する。
   - MarkItDown で変換し、変換結果のファイル・内容ハッシュ・再取得可能な成果物参照を取得する。許可済みのファイル読取機能でハッシュを照合して本文を読む際は、数十行ずつの細切れ読取を行わず、公開上限（`max_chars: 200000` 等）を使って少数の呼び出しで全文を欠落なく取得する（応答概要や検索結果だけで全文確認済みにしない）。読取ファイルが失われた・変化した場合は、同じ保存済み成果物参照から原バイト列を検証して復元し、再変換・全文転記しない。
4. **レビュー・結果保存**：
   - **仕様書 Markdown の最終保存**：検証済みの変換ファイルまたは成果物参照を使い、原バイト列を保ったまま区切り改行と短い `## RV 確認済みの適用範囲` 付記だけを末尾に追加する（モデルによる全文転記や別ファイル作成は禁止、原バイト列を保持できなければ変換・保存異常とする）。`PASS` / `FAIL` とも、この最終版を `レビュー/{testRunId}/{documentId}/テスト仕様書.md` に一度で保存・登録してから判定を保存する。保存後に付記を追加・変更せず、`specVersion` は元 Excel のハッシュのままとする。
   - **レビュー報告の条件付き保存**：`FAIL` の場合だけ `レビュー/{testRunId}/{documentId}/レビュー報告.md` を生成・保存する。`PASS` ではレビュー報告や `RV_RESULT` の成果物記録・参照を作らない。詳細な指摘は `FAIL` の報告にまとめ、独立したレビュー JSON ファイルは生成しない。
   - **DB 判定記録**：`PASS` / `FAIL` とも `test_automation.test_document` の対象 `(test_run_id, document_id)` の同一行へ保存する。`verdict`（text 列）と `rv_result`（同一表の jsonb 列、互換性のため `{"verdict":"PASS"}` または `{"verdict":"FAIL"}` の最小記録のみ）を一回の UPDATE で同時更新し、回読で一致を確認する。生成列 `spec_status`（`FAIL` から `NEEDS_SPEC_REVISION` を導出）には書き込まない。
5. **成果物登録と集計・報告**：
   - MinIO への保存成功ごとに `test_automation.test_artifact` へ、`テスト仕様書.md` は `MARKDOWN`、`レビュー報告.md` は `RV_RESULT` として登録する。参照は `documentLibraryId`、`bucket`、`objectKey`（メタデータの `path`、または `folder/name` の文書庫内相対パス）とし、`test_artifact.object_key`（および `relative_path`）には成果物の相対パス、`test_document.source_object_key` には元仕様書の相対パスを snake_case 列で記録する。物理ストレージキーと作業用ローカルパスは取得・保存時にだけ使い、業務参照には使わない。
   - 保存を終えた文書は判定が `FAIL` でも処理状態を `COMPLETED` にする。文書・実行の終了時は `status` と `finished_at` を同時更新し、対象・`PASS`・`FAIL`・処理異常の件数を集計する。完了報告に実行 ID、文書ごとの ID・版・判定・処理状態・保存した成果物パスを含める。次工程へ進めるのは `COMPLETED` ＋ `PASS` ＋保存済み仕様書 Markdown を満たす文書だけとする。

## レビュー規則

- **明確さと検証可能性**：宣言されたテスト範囲内で、対象、前提条件、操作、テストデータ、期待結果が理解でき、互いに矛盾せず観測・検証可能か確認する。要求 ID がなくても元の記述で対応付ける。
- **形式と対象範囲**：Given / When / Then は確認の観点であり、必須の記述形式にしない。境界値・異常系は目的と範囲に応じて確認し、正常系の操作確認だけを目的とする仕様書に追加ケースを要求しない。
- **自動化情報の非強制**：セレクター・画面情報、ツール名・引数、接続先・認証情報、保存・判定などの工程チェック項目を仕様書の必須情報にしない。実行環境や自動化手段の未設定は業務仕様の RV 不合格理由にしない。
- **指摘の根拠**：根拠箇所、重要度、影響、具体的な修正案を付ける。シート見出し・ケース ID・引用を使い、取得できないセル座標は推測しない。
- **変換結果の照合**：空セル由来の `NaN` や `Unnamed` を直ちに仕様不足としない。判断に必要な図・表・記述が変換で失われた疑いがあれば元 Excel と照合し、必要な内容を取得できなければ変換の処理異常とする（推測で `PASS` / `FAIL` を付けない）。

廃止箇所を除いた有効範囲の業務テストを理解・検証できれば `PASS`、原文に要求の矛盾・必須情報不足・検証不能な期待結果があれば `FAIL` とする。表記や任意の改善提案だけで `FAIL` にしない。

## 書式・改訂と対象範囲の引渡し

- **有効範囲と原文保持**：知識庫の表記・改訂規則に従い、廃止・対象外を除いた記述をレビューする。部分改訂は有効な記述と残る前提・依存・期待結果を対応付ける。変換本文と書式付記を削除・要約・清書せず、旧記述、削除線・背景色の範囲、凡例、出典、色付きの空白セルを残す。書式付記・凡例・表頭・改訂履歴は判定資料であり、業務ステップに数えない。追加の範囲ファイルは作らない。
- **未確認情報の区別**：変換結果の有効な静的書式に知識庫の規則を適用する。未評価・未検査・未取得の書式は「書式なし」とせず、対象・操作・期待値を左右する不明点だけ照合する。必要な情報の変換欠落・取得不能は処理異常、原仕様の矛盾・定義不足は RV 判定として区別する。
- **末尾付記（`## RV 確認済みの適用範囲`）**：「RV による付記（仕様原文ではない）」と `testRunId`・`documentId`・`specVersion` を記す。採用した規則と根拠、除外箇所、部分改訂の有効な記述、必要な知識上の条件を短く残し、ケース/ステップ ID、シート・セル範囲または原文行・引用で特定する。全手順は複写せず、除外・部分改訂がなければその旨だけでよい。全廃止なら有効対象 0 件と記し、範囲が未確定なら `PASS` にしない。付記は範囲と解釈の説明であり、操作や権限を追加しない。

## 文書別レビュー報告（`レビュー報告.md`）

日本語の Markdown（`text/markdown`）で、仕様書の担当者が修正箇所と理由を理解できる内容にする。報告の判定・件数・参照は保存記録と一致させ、タスク全体の完了報告で文書別報告の保存を代替しない。

- **結論**：文書名を含む見出し（ID をタイトルにしない）、`FAIL` とその理由、重要度別の指摘件数を先頭に置く。改善提案と後続処理を妨げる問題を区別する。
- **確認範囲**：対象のシート・ケース・要求、確認した観点、関連仕様の不足や変換による情報欠落を簡潔に示す。未確認の範囲を確認済みとしない。
- **指摘一覧と詳細**：一覧は番号・重要度・対象箇所・問題の短い表とし、長文を表へ詰め込まない。詳細は指摘ごとの見出しに分け、指摘番号で対応付けて原文の引用、問題と影響、具体的な修正案を記す。
- **次の対応と参照**：修正・確認すべき事項と次工程へ進める条件を示し、末尾に元文書のパス、`testRunId`、`documentId`、`specVersion`、保存済み仕様書 Markdown の参照を記す。

## 異常と同一実行の継続

- **対象 0 件・文書単位の異常**：当日更新分が 0 件なら `NO_TARGETS` と件数 0 を記録する。明示選択されたファイルの不存在は処理異常とする。取得・変換・保存の異常は対象文書を `FAILED` にして他文書を処理する（RV 未実行なら判定は未設定、判定後なら得られた判定を保持）。
- **タスク終了時の確定**：本実行の未完了の `test_document` と `test_run` を `FAILED` にし、`finished_at`・終了理由を記録して回読する。終端済みの状態と得られた判定は保持し、未レビューを RV の `FAIL` にしない。全体は処理異常がなければ `COMPLETED`、あれば `FAILED` とする（判定後の保存失敗では判定件数と処理異常件数が重複し得る）。
- **中断と同一実行の回復**：テスト管理 DB が利用不能なら中断し、実行 ID と保存済みパスを実行記録へ残す。同一実行の継続では、実行コンテキストの ID・保存先を DB と照合し、登録・保存済みの処理を重複実行せず未完了部分から回復する。確定済みの判定・適用範囲付記・最終 Markdown・報告本文を再利用し、再レビューや付記の重複追加、DB の最小判定からの指摘再構成、既存の旧形式 JSON・記録の書き換えは行わない。保存応答が不明なら元の保存要求を照合し、実行の同一性や書込み結果が不明なら停止して報告する。
- **実行 ID の管理**：継続用 ID は内部の実行コンテキストで保持し、利用者に `test_run_id` を入力させない。新しい依頼では対象パスが同じでも過去の実行 ID を流用しない。
