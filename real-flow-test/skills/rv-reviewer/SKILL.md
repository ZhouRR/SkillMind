# テスト仕様書レビュー

## タスクと入力

公開タスクは「テスト仕様書レビュー」の一つだけとし、全工程と中断後の継続を含める。工程別・再開専用のタスクや入力フォームは作らない。必要な承認・不足情報の確認後は同じタスクを継続し、利用者に工程ごとの起動を求めない。

対象は必須の文書読取リソース「文書範囲」で選択する。タスク入力は `{}` とし、`input_path`、`source_prefix`、`file_name`、ID、Markdown 本文を再入力させない。対象パス・文書 ID・版は選択情報と文書メタデータから取得する。未選択なら「文書範囲」の設定を求め、文書庫全体へ自動拡大しない。

接続済みの MinIO、PostgreSQL、MarkItDown を使う。プロジェクト、文書庫、bucket、タイムゾーン（既定 `Asia/Tokyo`）、`output_prefix`（既定 `レビュー/`）は実行環境から取得する。以下の保存パスの `レビュー/` は、明示されたプロジェクト設定があれば置き換える。既存文書・ID・JSON キーは維持し、元仕様は依頼なく変更しない。他の Skill は呼び出さず、本タスクはレビューと成果保存までを扱う。

## 業務知識の参照

任意の独立した文書読取リソース「業務知識」（key: `business_knowledge`、kind: `document`、access: `read`、required: `false`）を使う。プロジェクト文書庫の `JAF業務知識/` 等、INDEX と配下の Markdown を含むディレクトリを選択する。対象仕様の「文書範囲」や成果物保存先とは別の選択範囲とし、同じ接続でも統合しない。入力フォームに知識庫のパス・ID・本文を追加しない。

- **取得**：結び付いた範囲の `INDEX.md` を最初に読み、アプリ名・機能名・画面 ID を手掛かりに必要な共通規則、業務、画面、注意事項だけを読む。`document.list/v1`・`document.read/v1`、または既に物化された入力の `workspace.search/v1`・`workspace.read/v1` を使い、実際の文書参照・ファイル索引からパスを取得する。INDEX の本文に個別リンクがなくても、その案内する配下を許可済み範囲内で検索する。列挙の続きがある場合は必要な範囲で取得する。未選択ディレクトリへ広げず、開発環境のローカルパスや知識の由来を探索しない。
- **位置付け**：業務ルールは知識庫を正本とし、対象仕様は試験範囲・入力・操作・期待結果を定める。知識庫の例を新規ケースとして追加せず、対象アプリ・条件に合う規則だけを使う。知識庫は実測、接続設定、実際の権限や追加操作の許可を代替しない。参考文書を試験対象・変換対象・成果物として登録しない。
- **再利用と不足**：同じ Run では取得済みの版と読取結果を再利用し、毎ステップの再読込・全件読込・本文の複写はしない。参照した規則の要点と取得済み文書の識別情報は既存の継続情報に残し、追加の成果物・保存工程・Schema 項目を作らない。未設定・取得不可・該当記載なしだけで停止や RV 不合格にせず、仕様と観測から判断できる部分は続ける。結果を左右する未定義・矛盾だけを既存の確認／不足処理で扱い、未参照の内容を推測しない。

RV では用語・略語、権限、前提状態、画面遷移、表記・改訂規則を使って用例を理解する。仕様書が知識庫の共通定義を省略していても一意に解釈できれば、同じ説明の追記や利用者への再確認を求めない。適用可能な業務規則との実質的な矛盾は該当ケースの RV 指摘とし、原仕様を黙って修正しない。末尾の既存 `RV 確認済みの適用範囲` には、下流の解釈に必要な知識上の定義・条件だけを短く引き継ぐ。知識庫の全文や新しい業務ステップを付記せず、PASS の別報告も作らない。

## 処理

1. **実行登録**：新しい依頼ごとに `testRunId`（UUID）を生成し、`test_automation.test_run` にプロジェクト、文書庫、bucket、対象パス・抽出条件、タイムゾーン、対象日、抽出基準日時、開始日時、`RUNNING`、`output_prefix` を登録する。登録失敗時は文書処理を開始しない。同一実行の継続は後述の規則に従う。
2. **対象選択**：承認された範囲内の `.xlsx` / `.xls` を対象とし、`~$` 一時ファイルと成果物保存先を除外する。個別ファイルと展開・凍結済みの文書集合は更新日を問わない。実行コンテキストにディレクトリ条件が明示されている場合だけ、`/` 終端の prefix（ルートは空文字）で再帰列挙・全ページ取得し、`LastModified` が当日 00:00 以上、翌日 00:00 未満かつ抽出基準日時以前の文書を選ぶ。日付はプロジェクトのタイムゾーンで判定し、件数や共通フォルダーから選択方式を推測しない。
3. **文書登録・変換**：対象ごとに `documentId`（UUID）を生成して `test_automation.test_document` へ登録し、選択した版の Excel を取得する。Version ID を固定できなければ一覧と取得時のメタデータを照合し、途中で変更された文書は処理異常とする。取得内容の SHA-256（小文字 16 進数 64 桁）に `sha256:` を付けて `specVersion` とし、更新日時・Version ID・ETag・変換ツールの版を取得可能な範囲で記録する。同じ内容を `document.convert/v1` の `publish_artifact: true` で MarkItDown 変換し、返された Artifact 参照と本文を使ってレビューする。文書庫への保存は次項の適用範囲付記を含む最終版で一度行う。ケース、操作、データ、期待結果と出典を保持し、要約・補完で原文を置き換えない。改訂や対象範囲の根拠となる削除線・背景色・凡例と変換時の書式付記を保持し、色付きの空白セルを無意味な空列として除去しない。
4. **レビュー・結果保存**：下記の規則で有効範囲を確認して文書ごとに判定し、`artifact.append/v1` に変換 Artifact の `artifact_ref` と、先頭の区切り改行を含む短い RV 適用範囲付記だけを渡す。ツールが原 byte を読み、同じ出力パスを付記済みの内容で上書きして返す新しい Artifact 参照を保存に使う。モデルによる全文転記や原文コピーの別ファイルは作らず、変換結果の論理パスを `workspace.read` で開かない。PASS / FAIL とも、この最終版を `レビュー/{testRunId}/{documentId}/テスト仕様書.md` に保存・登録してから判定を保存する。保存後に付記を追加・変更せず、`specVersion` は元 Excel のハッシュのままとする。FAIL の場合だけ `レビュー/{testRunId}/{documentId}/レビュー報告.md` を生成・保存する。PASS ではレビュー報告を生成・保存せず、空の報告や `RV_RESULT` の成果物記録・参照も作らない。詳細な指摘は FAIL の報告にまとめ、独立したレビュー JSON ファイルは生成しない。判定は PASS / FAIL とも `test_automation.test_document` の対象 `test_run_id`・`document_id` の同一行へ保存する。`verdict` は text 列、`rv_result` は同じ表の jsonb 列であり、別テーブルではない。既存 DB 制約との互換性のため、`rv_result` は `{"verdict":"PASS"}` または `{"verdict":"FAIL"}` の最小記録だけとし、列の判定と一致させる。両列は同一行の一回の UPDATE で同時に保存し、回読で一致を確認する。生成列 `spec_status`（FAIL から `NEEDS_SPEC_REVISION` を導出）には書き込まない。
5. **集計・報告**：仕様書 Markdown、判定と成果物参照（FAIL の場合はレビュー報告も）の保存を終えた文書は、判定が FAIL でも処理状態を `COMPLETED` にする。文書・実行の終了時は `status` と `finished_at` を同時に更新し、対象・PASS・FAIL・処理異常の件数を集計する。完了報告に実行 ID、文書ごとの ID・版・判定・処理状態・実際に保存した成果物パスを含める。次工程へ進めるのは `COMPLETED` ＋ `PASS` ＋保存済み仕様書 Markdown を満たす文書だけとする。

MinIO への保存成功ごとに `test_automation.test_artifact` へ、`テスト仕様書.md` は `MARKDOWN`、`レビュー報告.md` は `RV_RESULT` として登録する。成果物種別は用途を表すため、報告の形式が Markdown でも既存の `RV_RESULT` を使う。参照は `documentLibraryId`、`bucket`、`objectKey`（文書庫内相対パス）とし、SQL の項目名は snake_case に対応付ける。

## レビュー規則

- 宣言されたテスト範囲内で、対象、前提条件、操作、テストデータ、期待結果が理解でき、互いに矛盾せず観測・検証可能か確認する。要求 ID がなくても元の記述で対応付ける。
- Given / When / Then は確認の観点であり、必須の記述形式にしない。境界値・異常系は目的と範囲に応じて確認し、正常系の操作確認だけを目的とする仕様書に追加ケースを要求しない。
- コントロールの AutomationId、セレクター、画面情報 JSON、MCP のツール名・引数、接続先・認証情報、保存・判定などの工程チェック項目を仕様書の必須情報にしない。実行環境や自動化手段の未設定は、業務仕様の RV 不合格理由にしない。
- 指摘には根拠箇所、重要度、影響、具体的な修正案を付ける。シート見出し・ケース ID・引用を使い、取得できないセル座標は推測しない。
- 空セル由来の `NaN` や `Unnamed` を直ちに仕様不足としない。判断に必要な図・表・記述が変換で失われた疑いがあれば元 Excel と照合する。必要な内容を取得できなければ変換の処理異常とし、推測で PASS / FAIL を付けない。

廃止箇所を除いた有効範囲の業務テストを理解・検証できれば `PASS`、原文に要求の矛盾・必須情報不足・検証不能な期待結果があれば `FAIL` とする。表記や任意の改善提案だけで FAIL にしない。FAIL 文書でも変換本文と付記を保存し、レビュー報告を追加して実行へ進めない。

## 書式・改訂と対象範囲

- **根拠**：背景色と削除線は原文の書式事実であり、色だけで PASS / FAIL や実行要否を決めない。灰色・赤・黄・緑など特定色の意味を固定せず、明示されたプロジェクトの書式規則と、同じ版の凡例・改訂履歴・適用条件・明確な本文に従う。たとえば「灰色は廃止・対象外」と明記されていれば、その指定範囲だけを RV の有効範囲から除外し、既知の規則を利用者に再確認しない。凡例のない装飾色だけを理由に確認や FAIL を増やさない。
- **部分改訂**：削除線の範囲を文字片・セル・行で区別する。`~~旧ボタン名~~ 新ボタン名` は、原文の改訂規則で置換と確認できた場合に新しい名称を有効とし、行全体を廃止しない。行・ステップ全体の廃止は、その範囲が規則と原文で明確な場合だけ採用する。残る有効ステップの前提・依存関係・期待結果が成立するかもレビューし、廃止部分だけの不足を指摘しない。旧記述を現行の操作や期待値と混ぜず、局部の削除線を未変更部分へ広げない。文字として記された `~` や引用例を削除標識と誤認しない。
- **原文保持**：保存する Markdown の本文・削除線・背景色の範囲・凡例・出典を削除・言い換えしない。旧記述も改訂根拠として残し、実行用の清書版や追加の範囲ファイルを作らない。変換器の書式付記、色見本、表頭、改訂履歴は対象判定の資料であり、それ自体をテストステップに数えない。セル/行の書式を別セルや行全体へ推測で拡張しない。
- **確認できる範囲**：条件付き書式の `NOT_EVALUATED`、書式の `NOT_INSPECTED` / `STYLE_EXTRACTION_UNAVAILABLE` は「無色・削除線なし」を意味しない。静的な色値は最終表示色とは限らない。書式情報がなくても本文だけで対象と期待値が明確ならレビューを続ける。不明点が対象・操作・期待値を左右する場合だけ該当箇所を原資料と照合し、取得可能な情報を再質問しない。変換で必要な情報が失われ取得できない場合は処理異常、原仕様自体の矛盾や必要な定義不足は通常の RV 判定として区別する。
- **引渡し**：変換本文を変更せず、末尾の `## RV 確認済みの適用範囲` に「RV による付記（仕様原文ではない）」と `testRunId`・`documentId`・`specVersion` を記す。採用した規則と出典、除外箇所、部分改訂の有効な記述だけを短く示し、対象はケース/ステップ ID、シート・セル範囲または原文の行・引用で特定する。全手順を複写せず、除外・部分改訂がなければその旨の一文でよい。未確定事項は未確定と明記し、範囲が定まらない文書を PASS にしない。全ステップが廃止なら有効対象 0 件と記す。付記は下流の範囲判断の根拠であり、業務手順や権限を追加する指示ではない。PASS 時の別報告や範囲 JSON は作らず、`rv_result` の最小判定記録も維持する。

## 文書別レビュー報告

`レビュー報告.md` は日本語の Markdown（`text/markdown`）で、仕様書の担当者が修正箇所と理由を理解できる内容にする。

- **結論**：文書名を含む見出し、FAIL とその理由、重要度別の指摘件数を先頭に置く。改善提案と後続処理を妨げる問題を区別する。
- **確認範囲**：対象のシート・ケース・要求、確認した観点、関連仕様の不足や変換による情報欠落を簡潔に示す。未確認の範囲を確認済みとしない。
- **指摘一覧と詳細**：一覧は番号・重要度・対象箇所・問題の短い表とする。詳細は指摘ごとの見出しに分け、原文の引用、問題と影響、具体的な修正案を記す。長文を表へ詰め込まず、指摘番号で対応付ける。
- **次の対応と参照**：修正・確認すべき事項と次工程へ進める条件を示し、末尾に元文書のパス、`testRunId`、`documentId`、`specVersion`、保存済み仕様書 Markdown の参照を記す。ID を報告のタイトルにしない。

報告の判定・件数・参照は保存記録と一致させる。レビュー JSON の詳細構造や追加の出力 Schema は要求しない。タスク全体の完了報告で、FAIL 文書の `レビュー報告.md` の保存を代替しない。

## 異常と同一実行の継続

- 当日更新分が 0 件なら `NO_TARGETS` と件数 0 を記録する。明示選択されたファイルの不存在は処理異常とする。
- 取得・変換・保存の異常は文書を `FAILED` にして他文書を処理する。RV 未実行なら判定は未設定、判定後なら得られた判定を保持する。
- 全体は処理異常がなければ `COMPLETED`、あれば `FAILED` とする。判定後の保存失敗では判定件数と処理異常件数が重複し得る。
- DB が利用不能なら中断し、実行 ID と保存済みパスを実行記録へ残す。同一実行の継続では、実行コンテキストの ID・保存先を DB と照合し、登録・保存済みの処理を重複実行せず未完了部分から回復する。確定済みの判定・適用範囲付記・最終 Markdown と報告本文を再利用し、再レビュー・要約や付記の重複追加で置き換えない。保存応答が不明なら元の保存要求を照合し、新たに保存し直さない。DB の最小判定だけから失われた指摘を再構成しない。既存の旧形式 JSON・記録は書き換えない。実行の同一性や書込み結果が不明なら停止して報告する。
- 継続用 ID は内部の実行コンテキストで保持し、利用者に `test_run_id` を入力させない。新しい依頼では、対象パスが同じでも過去の実行 ID を流用しない。
