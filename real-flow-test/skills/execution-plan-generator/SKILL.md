# テスト実行

## タスクと入力

公開タスクは「テスト実行」の一つとし、RV 済み Markdown を直接実行し、実測と成果物を保存する。既存登録との対応のため Skill 識別子は維持する。独立した実行計画の生成・検証・保存・状態管理は行わず、`test_execution_plan` への新規登録・旧計画の再利用を前提にしない。内部工程の起動や画面情報ファイルの事前提出を利用者に求めない。他の Skill は呼び出さず、最終判定の起動はプラットフォームに任せる。

対象は「文書範囲」で選択した RV 済み Markdown、または実行コンテキストの文書参照から特定する。選択済みならタスク入力は `{}` とし、パス・ID・本文を再入力させない。`test_automation.test_run`、`test_document`、`test_artifact` の保存記録から、選択した Markdown に対応する `testRunId`、`documentId`、`specVersion` を引き継ぐ。一意でなければ対象を確認し、過去の PASS を暗黙に選ばない。

仕様本文の入力はこの Markdown のみとする。元 Excel の取得・読取・再変換・版照合を行わず、利用者に Excel の提出やパス・シート・セル情報の入力を求めない。元 Excel のファイル・保存先・Version ID・ETag・シート名・セル座標が提供されなくても、それを理由に停止しない。

接続済みの MinIO、PostgreSQL、Schema 検証ツール、実行対象の Runner／MCP を使う。DB の表はすべて `test_automation` Schema に属する。登録 appId と環境・対象ビルドの版は、接続済み環境の公開設定・読取結果、または監査済みの回答から取得する。接続参照はプラットフォームの binding を使い、仕様書への追記や秘密情報の入力を求めない。未提供の環境設定を工具清單・アプリ名から推測しない。

## 新規テストと旧実行の復旧

新しく開始された Run は、利用者が旧実行の継続・記録復旧を明示した場合を除き、選択 Markdown に基づく独立したテストとして扱う。旧計画や `ABORTED` の履歴が見つかっただけで復旧へ切り替えない。待機への回答で「現環境版で再テスト」が選ばれた場合も、現在の Run で新規実行の準備を続ける。「別依頼」は旧実行とは別の業務実行を意味し、同じタスクを起動し直すよう求めない。SKM の Run ID と RV 由来の `testRunId` は別の識別子であり、新規テストでも RV の ID は引き継ぐ。

旧処理の停止と占有競合の解消が確認され、新規テストの現在の前提条件が成立するなら、過去の `UNKNOWN` や未保存成果だけを理由に新規テストを止めない。原操作の結果は不明のまま保存し、旧要求を再送・成功扱いせず、新しい `executionId` と操作 ID・時間枠を使う。旧処理の稼働、未解消の pending、現在の対象状態への具体的な影響が残る場合は、その競合・前提だけを確認する。中断状態への DB 更新だけで原操作の終了や結果確定を推測しない。

旧操作記録の追加読取は明示された復旧に必要な場合だけ求める。新規テストの前提に旧記録の復元を加えない。復旧を打ち切る指示では不足と結果不明を報告して終了し、新規テストや旧データの書換えへ勝手に移らない。

## 前処理

1. 選択した Markdown に対応する保存記録で RV が `COMPLETED` ＋ `PASS` であることを確認し、RV 済みの保存済み `MARKDOWN` を取得する。判定と文書の対応は登録記録で確認し、元ファイルへのアクセスを確認条件にしない。
2. `test_execution` の実際の表構造を確認する。直接実行には `execution_basis`（JSONB）と NULL を許す `plan_id` が必要。RV 文書への対応は保存記録と DB 制約で維持する。未移行なら必要な DB 移行を明示して停止し、架空の計画 ID・空計画・旧計画の流用で制約を回避しない。他の処理の稼働や未解消の pending は確認し、旧履歴だけを理由に新規実行を止めない。
3. 実際に提供された MCP ツールと入力契約、対象アプリ、証跡取得・文書庫保存機能を確認する。Resources の読取権限だけではツールを実行できない。ツール呼出し機能がない場合は不足として返し、架空の URI やツール名、未許可の接続手段で代替しない。
4. `mcp.tools/v1` が提供される場合は `reserve_desktop: true` で工具契約・接続参照・サービス版と本 Run のデスクトップ予約を取得する。`desktop.lease_ref` を `environmentLease` に用い、`pending_operation` が true なら原操作の照合まで進めない。対象 Windows デスクトップは実行中の専用利用が手配済みで、手動操作・別システムの操作は入らないことを既定の運用前提とし、開始時・継続時に利用者への確認を求めない。SKM の予約は同一 endpoint の Run 間だけの排他であり、外部排他の技術的な保証とは区別する。`external_exclusivity: NOT_VERIFIED` だけを理由に停止・質問しない。実際の占有競合や外部操作を検知した場合、または必要な予約を取得できない場合は、後続操作を停止して具体的な不足・競合を報告する。
5. 許可済み工具に `get_environment` があれば、その入力 Schema に従って `mcp.query/v1` から呼び出し、`applications` の登録 appId・sutBuild、`environmentVersion`、`runnerVersion`、時間制限と同時利用条件を取得する。別名の環境取得工具がある場合も実際の説明・契約に従う。取得できる項目を利用者に再入力させない。版の取得にアプリの起動・画面検査を前提としない。`server.version` は MCP サービス版として `runnerVersions["mcpServer:" + server.name]` に固定し、実操作が返す `runnerVersion` と区別する。モデルは Brief の `runtime_metadata.model` を `modelVersion` とする。これは設定モデル ID であり内部ビルド番号ではない。環境版・対象ビルドなど取得経路がない必須値は、不足する項目だけをまとめて確認する。未提供の機能名で呼び出したり、`inspect_window` を環境設定の取得手段にしたりしない。

## 実行前の根拠固定

1. Markdown 全体から対象範囲の全ケース・業務ステップと元の期待条件を確認する。ケース・ステップ ID がなければ文書内の順序から安定した ID を付ける。対象範囲を後から実行済み操作だけに狭めず、前提条件・データ・後処理も原文に従う。
2. [execution-basis.schema.json](schemas/execution-basis.schema.json) に従う小さな `executionBasis` を作る。`sourceMarkdown` は取得元の文書参照と原バイト列の SHA-256、`specVersion` は RV 登録値とする。改行・空白を正規化してハッシュを作らない。`cases[].steps[]` に ID、原文の操作位置 `sourceLines`、期待条件の位置 `expectedLines`、必要な先行ステップ `dependsOn` だけを記録する。行番号は取得した UTF-8 Markdown の先頭を 1 とする包含範囲。範囲が実在し原文を正確に指すこと、全対象の網羅、ID の一意性、依存先の存在と非循環を実行前に検証する。期待条件が特定できなければ不足を確認し、創作しない。全文・手順配列・MCP 引数の写しを別の計画ファイルにしない。
3. `environment` に確認済みの appId・接続参照・予約参照、並列度 1、ケース時間制限を保持する。環境・タスクの指定を優先し、指定がなければケース 1800 秒、単独操作 15 秒を既定として工具上限内に収める。ケース時間は最初のアプリ準備から測り、承認・中断待ちを含め継続時にリセットしない。期限後は新操作を提案せず、進行中の操作は原 ID で照合する。送信・登録等の非冪等操作は自動再試行せず、仕様にない削除・終了を追加しない。
4. `versionSnapshot` に Skill の固定版または checksum、確認済み環境・対象ビルド・Runner・モデル版を保持する。`executionBasis` の Schema・format と原文対応を検証し、次項の実行登録に `execution_basis`、`version_snapshot` として一度に保存・回読する。実行前に永続化できなければ操作しない。独立した根拠ファイルの公開・完了状態・計画生成試行回数は作らない。登録後は根拠・期待条件・固定版を変更せず、結果にも同じ値を引き継ぐ。

## 画面確認と MCP 実行

1. 新規テストごとに `executionId`（UUID）を発行する。準備完了後、`test_execution` に `execution_id`、RV の `test_run_id`・`document_id`、`execution_basis`、`version_snapshot`、`status: RUNNING`、`started_at` を一度に登録し、`plan_id` は NULL とする。承認・適用・回読が確認できてからアプリを操作する。同一実行の継続は既存 ID と登録済み根拠を使い、再登録・再構成しない。
2. FlaUI では実行登録後に `open_application` を提案して登録アプリを準備する。起動には `requestId: "${effect_id}"` を渡し、同じ ID の `get_step_status` で原要求の回执を確認する。`READY` の場合だけ `inspect_window` で現在画面と対象コントロールの操作可否を確認して業務ステップへ進む。保存済みの起動回执は現在の画面・生存を保証しない。取得済みの画面情報は画面変化や不足がない間は再利用する。同じ実行の既存準備回执が確認済みなら起動を繰り返さない。`inspect_window` はアプリを起動しない。ウィンドウ・コントロールを現在の情報から特定し、画面遷移後は再取得する。対象が複数なら観測で絞り込み、業務上の対象を一意に判断できなければ停止して確認する。
3. 元の業務ステップに必要な操作を `execute_step` で一つずつ提案し、承認済み操作をプラットフォーム経由で実行する。提案前に入力をツール契約と照合し、`executionId`・ケース ID・`stepId`・操作内容を記録する。提案にもこの対応を示し、送信前の要求と提案参照はプラットフォームの監査記録で保持する。`requestId` はプラットフォームが操作ごとの Effect UUID として供給するため、独自に生成せず、実値の代わりに呼出し引数の `requestId` へ予約値 `${effect_id}` を指定する。汎用 MCP 提案は `operation: "call"`、`target.locator` を実際の工具名とし、`/call` の値に `arguments` と `read_back` を指定する。`execute_step` の回読は `get_step_status` とし、同じ予約値を照会引数と `/requestId` の equals 条件に使い、`/status` は `COMPLETED / ERROR / TIMEOUT / CANCELLED / ABORTED` の one_of 条件で終端を確認する。回読の JSON Pointer と比較値は実際の `output_schema`、公開された返却契約または同じ工具の観測済み応答に基づく。入力引数の存在から返却フィールドを推測しない。`open_application` の回読も `get_step_status` を使い、同じ `/requestId`、登録済み `/appId`、`/status` の `READY / ERROR / TIMEOUT / CANCELLED / ABORTED` を確認する。失敗終端の一致は結果確定であり起動成功ではない。`READY` 以外では業務操作へ進まず異常時の記録へ移る。起動と各業務操作にはそれぞれ別の Effect が供給する ID を使う。正式な操作 ID を実行結果・監査記録から取得後、元の提案と業務ステップへ対応付けて操作記録を補完する。提案時点で未発行の `requestId` を要求して停止しない。
4. 応答が `RUNNING`、通信切断、応答不明なら、原要求に実際に渡されたことを確認できる `requestId` を許可された `get_step_status` で照会する。旧版の起動など要求 ID を送っていない操作では、Effect UUID を Runner の要求 ID とみなして照会しない。ID がまだ取得できない場合はプラットフォームによる元の操作の結果照合を使い、推測した ID や新しい提案で送り直さない。取消しの `cancel_step` にも取消対象の原 ID を渡し、提案の `/call` に `cancel_target` としてその Effect UUID を指定する。回読は同じ原 ID と終端・取消確認を条件とし、終了状態と現在画面を確認する。照会不能や操作済みか不明な状態では後続操作を止める。
5. 操作完了後に画面・値を再取得し、原文の期待条件に対応する実測を収集する。必要なスクリーンショットや読取結果も元の業務ステップへ結び付ける。表示内容と UI API の値表現が異なる場合は生値と解釈理由を残し、期待値の変更や一律の文字除去で一致させない。
6. 操作失敗・期待条件との不一致・前提未成立なら、その状態に依存する後続操作を止め、残りを `NOT_RUN` とする。正常な前提で実行できる独立ケースのみ継続できる。確認のために送信・登録を繰り返さず、時間制限で観測を打ち切る。

FlaUI の `select_row` では、一覧の定位条件と行内セルの照合条件を分ける。`cells` は対象行のデータセルの AutomationId をキー、空でない完全一致文字列を値とする object とし、公開契約に `inputs` があれば構造化入力を使う。`inspect_window` の `index`・`parentIndex`・`controlType` から一覧 → 対象行 → セルの所属を確認し、表頭の `HeaderItem`、表示上の列名、列番号をセル ID の代わりに使わない。たとえば行内セルとして観測された `ListViewSubItem-0` を使い、表頭の `HeaderItem 0` から ID を推測・変換しない。照合値は同じ行の観測と仕様上の対象に基づき、照合に使わない空欄は条件へ加えない。階層やセル ID が不足する場合は許可された画面観測で補い、一意に特定できるまで選択を提案しない。

## 実行成果の保存と返却

- 既定の保存先は `実行結果/{executionId}/` とする。プロジェクト設定を優先し、継続時は同じ保存先を使う。`操作記録.json` に操作前の業務ステップ・要求内容と、取得後の提案参照・正式な操作 ID・応答・画面情報・時刻を保存する。プラットフォームの原監査記録と照合し、補助操作も元のケース・ステップへ対応付ける。未取得の ID を捏造せず、保存失敗時は次の操作へ進まない。
- FlaUI の単独操作結果を [execution-result.schema.json](schemas/execution-result.schema.json)（`schemaVersion: 2.0`）に集約して `実行結果.json` を作る。登録済み `executionBasis` の全ケース・ステップを含め、未実行や実測不明を省略・成功扱いしない。`executionBasis`、ID・`versionSnapshot` は DB の登録値をそのまま引き継ぐ。
- Runner の `downloadPath` はローカル証跡の取得先であり文書庫参照ではない。許可された取得機能で実体を取得し、文書庫へ保存してから Evidence の参照を設定する。操作記録は `TRACE`、実測は `ACTUAL_OUTPUT` 等の契約上の種別で元ステップに関連付ける。取得できない証跡は不足として記録する。
- 全必須ステップを実行できた場合の `COMPLETED` は実行状態であり、テストの PASS ではない。操作異常や前提未成立による未完了は `ERROR`、実行の時間制限超過は `TIMEOUT`、取消し・中断は `ABORTED` にまとめる。FlaUI の `CANCELLED` は共通契約の `ABORTED` に対応付け、元の状態と理由を操作記録へ残す。
- 構造化出力の修正は初回を含め最大 3 回とし、UI 操作の再実行に流用しない。集約結果の Schema・format、DB の実行根拠との ID・版・ステップ集合の完全一致、実測と保存済み Evidence を検証する。同じ種類の環境・対象ビルド・Runner 版が固定値と異なる場合は停止し、登録値で覆い隠さない。MCP サービス版と操作応答の `runnerVersion` は別の識別体系として扱い、文字列の違いだけで不整合にしない。固定時に未取得だった操作 Runner 版は操作記録に保存し、固定済み `versionSnapshot` を書き換えない。結果保存後、実際の文書参照を `test_execution.result_ref` に記録し、終端状態と `finished_at` を同時更新する。保存失敗を実行成功として返さず、取得済み結果から保存を再開できるようにする。
- ID、実行の状態、件数、保存済みパス、未実行・証跡不足・異常理由を返す。MCP 呼出し成功や画面の変化だけから、仕様の確認範囲を超えた結果を断定しない。最終的な Verdict・原因分類は生成しない。

## 異常と継続

MCP の失敗は呼出し・回読・条件照合のどこで起きたかを区別し、元の Effect ID、診断 ID、取得済み観測の参照を保持する。起動済みでも回読失敗なら後続の入力・送信へ進まない。アプリ未起動・パス不一致・Windows セッション・読取権限は診断前に断定せず、応答不明の操作を新規 ID で再送しない。

プラットフォームが未送信または原操作の終端を確認して同じ Run を続行した場合、失敗が解消できなければ未実行ステップを `NOT_RUN` とし、実行を `ERROR`（時間超過は `TIMEOUT`、取消しは `ABORTED`）として `finished_at`・エラー・取得済み結果を既存 ID に保存・回読する。固定済みの実行根拠は維持する。結果未知は確定した操作失敗と区別する。プラットフォームが Run を終止した場合は後続の保存が実行されたとみなさず、原操作の核対と残った記録更新が必要であることを明示する。

実行登録前の情報・機能不足は `BLOCKED`、ツール異常・修正上限は `FAILED` とする。実行登録後は実行表の状態を使い、存在しない `BLOCKED` を書き込まない。DB 書込みは利用環境の許可・承認手順と回読に従い、既に認められた範囲で工程ごとの追加確認を要求しない。DB が利用不能なら操作を止め、ID と保存済みパスを実行記録へ残す。

明示された旧実行の継続・記録復旧では、前の処理の終了、DB、操作記録、プラットフォームの原監査記録と照会可能な Runner の要求状態を照合する。既存 ID・固定版・期限を維持し、完了済みの RV・操作を再実行せず未完了部分だけを回復する。記録保存だけが未完了なら取得済み結果から補完し、操作を再送しない。照会可能な原 ID や必要な記録がなければ復旧不能な範囲を明示する。旧計画方式の実行は当時の凍結 Skill・Schema で扱い、現行形式へ変換して続行しない。
