# テスト実行・原記録索引の保存

## 目的と役割

RV を通過したテスト仕様書 Markdown と業務知識に従い、テスト環境の操作ツール（MCP Runner 等）を用いて被測アプリケーションのテスト手順を実際に実行し、操作回執と画面観測の参照索引を保存・要約する。最終的な業務合否（PASS/FAIL）の判定は後続の結果判定工程に委ね、他の Skill の呼び出しは行わない。

- **参照 Schema**：
  - 実行開始前に固定する最小実行根拠：[execution-basis.schema.json](../../schemas/execution-basis.schema.json)
  - 終了時に保存する原記録の参照索引：[runner-records.schema.json](../../schemas/runner-records.schema.json)（`schemaVersion: "2.0"`）
- **一貫完遂と未収尾終了の厳禁（最重要）**：
  - 前処理・環境確認や最初の数ケースを実行しただけの段階で勝手にタスクを打ち切って終了することを厳禁する。全体を継続できない環境障害や実行時間・予算の上限に達しない限り、**有効な全テストケースを順序通り最後まで連続して実行する**。
  - 全ケース完了時、またはやむを得ない理由で途中終了・中断する場合でも、**終了前に必ず「実行済み操作の履歴保存 → `runner-records.schema.json` に従う参照索引（`result_ref`）の作成・検証 → 管理記録の終端状態への更新」までを完了し、実行状態を `RUNNING` のまま残して終了してはならない**。

## リソースの確立と業務知識の段階的参照

1. **対象仕様書と管理記録の確立**
   - 実行コンテキストから RV 済みの仕様書 Markdown（および対応する `testRunId`・`documentId`・`specVersion`）を特定して取得する。文書参照の `objectKey` には文書メタデータの論理相対パス（`path` または `folder/name`）を使用し、物理ストレージキーや一時ローカルパスと混同しない。元 Excel の再取得や再変換は行わない。
   - **テスト管理記録（接続されている場合）**：利用可能な管理テーブルの構造を確認し、RV 状態の照合、実行開始（`RUNNING`）と実行根拠（`execution_basis`）・バージョン情報（`version_snapshot`）の登録、および終了時の参照索引（`result_ref`）と終端状態の更新に使用する。
   - **被測システムの業務データベース（任意）**：仕様書のデータ参照・準備・更新確認、および画面操作による業務データ変更の観測に使用する。接続された実際のテーブル・列・権限の範囲内で対象を特定する。業務データベースが未接続・利用不能な場合は、その接続を必須とする手順と依存部分のみを理由付きで未実行（`notRun`）とし、独立して実行可能なケースは継続する。

2. **テスト環境と操作ツールの探査・再利用**
   - 初回にテスト環境の操作サービス（MCP 等）が公開するツール一覧と入出力 Schema、対象アプリケーション設定、環境予約（Lease）、およびバージョン情報（環境版 `environmentVersion`、対象ビルド `sutBuild`、実操作の `runnerVersions`、現在の `modelVersion`、実行中の `skillVersion`）を一括して確認し、同一実行内で再利用する。操作のたびに同じツール定義リソースを繰り返し細切れに読み直さない。
   - 利用者が旧実行の継続・復旧を明示した場合を除き、新しい独立したテスト実行（新規 `executionId`）として扱う。環境予約機能が公開されている場合は予約を取得して `environmentLease` に保持する。
   - 本タスクに提供されたテスト用デスクトップは既定で専用利用とし、専用利用の再確認を求めずに実行する。

3. **業務知識の段階的参照（全件一括読取の禁止）**
   - **開始時・実行登録前（`RUNNING` 登録まで）**：最初はプロジェクト文書庫の業務知識索引（`INDEX.md`）と共通の仕様書表記・改訂規則のみを読む。さらに `INDEX.md` の収録一覧から、試験対象の入口（起動・ログイン）と主画面に関する基本文書および共通の既知制約のみを選択して読み、先に `executionBasis` の検証と実行開始（`RUNNING`）の登録を完了する。知識庫内の全ファイルを無差別に一括読取しない。
   - **ケース実行中（オンデマンド追加読取）**：子画面への遷移や個別業務機能のテストケースを実際に操作する時点で、`INDEX.md` の一覧から該当する機能・画面の文書のみをオンデマンドで追加読取し、同一実行内で再利用する。

## ツールの使用と受控書込・回読（`read_back`）の原則

1. **大判文書・大きな回執の効率的読取**
   - 仕様書 Markdown 全文や大きな操作回執を読む際は、数十行ずつの細切れ読取を行わず、読取ツールの大きな文字数・行範囲や構造化抽出機能（JSON Pointer 等）を使って少ない呼び出し回数で必要な範囲を欠落なく確認する。

2. **操作実行における回読確認（回執の確定と業務成否の分離）**
   - 受控書込（提案・承認・適用・回読）を通じてテスト環境の操作ツールを呼び出す際、ツール層の回読確認（`read_back`）は「操作が業務上必ず成功したこと」を断言するためではなく、「**テスト実行器（Runner）が当該呼出しの結果を原要求 ID に対応付けて記録し終えたこと**」を確認するために設定する。
   - 画面操作やログイン等は成功だけでなくタイムアウトやエラーで終了する場合があるため、回読の検証条件では状態を単一の成功値（`COMPLETED` のみ等）に固定せず、実行器が返し得るすべての終端状態（例：`COMPLETED`、`ERROR`、`TIMEOUT`、`REJECTED`、`CANCELLED`、`ABORTED` 等）を許容して回執を受け取る。保存処理では、ツール契約上その呼出しが終了し続行可能な部分完了も受け取り、全件保存の完了とは区別する。
   - 回執を受け取った後、回執内の実際の状態とエラー内容を Agent 自身が確認して次の行動を判断する：
     - 正常に完了していれば次のステップへ進む。
     - ログイン入力の応答タイムアウト、一時的なフォーカス外れ、ダイアログ表示など回復可能な失敗であれば、現在のウィンドウ・画面状態を再観測した上で適切に再試行する。
     - 進行中や通信一時断で結果が未確定の場合は、送信した要求 ID または返却された操作 ID で状態照会ツールを呼び出して確認し、闇雲に同じ非冪等操作を重複送信しない。

## テスト実行のフロー

1. **全有効ケースの特定と実行根拠（`executionBasis`）の固定・開始登録**
   - 仕様書 Markdown 全文と末尾の `## RV 確認済みの適用範囲` を確認し、廃止・除外箇所を除いた有効な全テストケースを特定する。有効対象が 0 件なら対象なしとして終了する。
   - [execution-basis.schema.json](../../schemas/execution-basis.schema.json) に従い、ケース単位の最小実行根拠を作成して Schema 検証を行う：
     - `sourceMarkdown`：取得元 Markdown の文書参照と原バイト列の SHA-256。
     - `specVersion`：RV で記録された元仕様書の SHA-256。
     - `cases[]`：有効な各テストケースにつき、ステップサフィックスを除いたケース単位の `testCaseId` と、当該ケースの操作・期待条件が含まれる UTF-8 Markdown の 1 始まり包含行範囲 `sourceLines`（`{"start", "end"}`）を記録する（期待条件が別行範囲にある場合のみ `expectedLines`、他ケースへの先行依存がある場合のみ `dependsOn` を指定）。
     - `environment`：確認した `appId`、`connectionRef`、`environmentLease`、`maxParallelism: 1`、`caseTimeoutSeconds`（未指定時は 1800 秒を既定）を設定する。
   - 新規 `executionId`（UUID）を発行し、検証済みの `executionBasis` と `versionSnapshot` を管理記録へ `status: RUNNING` として登録・回読してからテスト環境の操作を開始する。

2. **環境の準備とテスト手順の実行**
   - ケースの最初の操作から、準備・業務操作・表示確認をケース ID と短い名称による同じ区分にまとめて保存する。共通準備は別区分とする。
   - **自律的な環境準備（`PREPARATION`）**：入口アプリケーションと被測アプリケーションを区別し、現在のプロセス・ウィンドウ状態を観測して、起動・ログイン・ウィンドウ切替・初期状態の整備・確認ダイアログ処理を自律的に行い、対象ケース/ステップの `PREPARATION` として記録する。ログイン操作では秘密値を出力・転記せず、認証情報入力の完了と認証成功後の画面遷移を区別して確認する。
   - 予期しないエラーやアプリ終了時は、原回執・メッセージと現在の状態から、ダイアログ処理・再起動・状態復元を自律的に判断する。復旧できないケースと依存部分は理由付きでスキップし、独立した後続ケースを継続する。
   - 入力後に進めない場合は、直前の項目の失焦時検証も含めてエラー項目と条件を確認する。試験対象外の準備データは条件に合わせて修正して継続し、使用値を記録する。入力値・入力検証自体が試験対象の場合は、指定値と実際の検証応答を実測として残す。
   - **業務操作（`BUSINESS`）と画面観測（`OBSERVATION`）**：仕様書の各ケース・ステップに従い、観測した要素情報に基づいて操作を実行する。同一ウィンドウ内で対象と順序が確定している連続操作は短いステップ列（最大 5 手順以内）にまとめてよいが、ログイン、ポップアップ、ウィンドウ遷移、動的判断の前では必ず区切って状態を確認する。画面を閉じる・遷移する前に確認が必要な表示はスクリーンショット等で撮影し、`OBSERVATION` として記録する。
   - 画面操作で業務データを変更する場面では、Agent が関連するレコード・列を特定し、利用可能な業務データベースから操作前・操作後のスナップショットを読み取り証跡として保存する。対象キー・観測時刻・ケース／ステップ・原操作 ID と対応付け、取得できない分は不足として残す。
   - 現在の業務知識・仕様書と利用可能な環境・操作機能では完了できない手順は、追加確認を待たず当該手順と依存部分を理由付きでスキップし、独立して実行できる後続ケースを継続する。
   - 原文の期待条件と実測をケース・ステップごとに対応付け、原回執と保存済み証跡への参照を記録する。操作とその表示確認は同じケースに関連付け、共用する観測は同じ参照を使う。

3. **UI 要素の定位と同名ノード衝突・要素一覧打ち切りへの対処**
   - 画面上に同じ名称（`name`）の要素や無名要素が複数存在する場合、あるいは名称指定で複数一致（`AMBIGUOUS_ELEMENT` 等）が返った場合、**直ちに定位不能として停止・未実行（`notRun`）にせず、画面の文脈から対象となる 1 ノードを判断して操作を試行する**：
     1. **操作可能な親コントロールの選択**：UI ツリーではボタン・チェックボックス・ラジオボタン・見出し等の親コントロールとその内部のテキスト子要素が同じ `name` を持つことがある。操作対象には必ず操作可能な親コントロール型（`Button` / `CheckBox` / `Edit` / `ComboBox` 等）の `automationId` または `elementId`（`windowId` 併用）を選択して試行する。
     2. **識別子の業務意味・近傍ラベル・領域配置による文脈特定**：同一画面内に同名のボタン（参照・クリア・選択等）や無名の入力欄・トグルボタンが複数ある場合は、`automationId` が表す項目名、直前・隣接するテキストラベル要素との座標位置関係（`boundingRectangle`）、画面内の所属領域（左右の列・グループ枠・下部バー等）、および補助スクリーンショットを照合し、当該ステップの操作対象に合致する 1 ノードの `automationId` または `elementId` を特定して試行する。
     3. **要素一覧の打ち切り（`truncated: true`）時の補完と試行**：ウィンドウ内の要素数が上限に達して一覧が打ち切られ対象要素が見えない場合は、①補助スクリーンショットで確認したボタンやラベルの正確な表記（全角空白等の有無を含む）を用いた指定を試行する、②テスト対象外の展開済みツリーや一覧要素が要素枠を大量に消費している場合は一時的に折りたたんで（`collapse`）からウィンドウ再観測を行い、後続の対象要素の識別子を取得して操作を試行する。
   - 要素情報による特定が難しい場合は、ツールが対応していれば現在の対象ウィンドウのスクリーンショットを使って操作する。画面変化後は画像を更新し、操作後の状態を確認する。

4. **履歴保存・参照索引（`result_ref`）の作成・終端更新と返却**
   - **原履歴・ログの保存**：実行終了時に履歴・証跡の保存機能が利用可能な場合は、本実行で完了した原操作の履歴や必要なログを保存し、保存回執から文書参照と SHA-256 ハッシュを確認する。
   - 保存が部分完了で戻った場合は、確認済みファイルと未送信分を照合し、ツール契約に従って同じ保存要求 ID・同じ対象集合で未完了分を続行する。結果不明分は原 ID で照会し、画面操作は再実行しない。保存の不足が残っても参照索引と管理記録の終端更新まで進める。
   - **参照索引（`result_ref`）の作成と Schema 検証**：[runner-records.schema.json](../../schemas/runner-records.schema.json)（`schemaVersion: "2.0"`）に従い、`execution_basis.cases` の全ケースを母集団として参照索引を作成・検証する：
     - `operations`：実行した各操作について `testCaseId`・`stepId`・`role`（`BUSINESS` / `PREPARATION` / `OBSERVATION`）・`connectionRef`・`requestId`・`confirmation`（終端回執を確認できた操作は失敗終端も含め `CONFIRMED`、結果不明は `UNCONFIRMED`）・`records`（確認済みの `locator`・`sha256`・保存先 `archive`）を記録する。業務データの前後スナップショットも該当操作の `records` に関連付ける。
     - `notRun` / `gaps` / `reasons`：未送信の業務ステップは `notRun`、操作 ID 不明・証跡や保存の不足は `gaps` に記録する。**ケース全体が同一理由で未実行または不足となった場合は、個別ステップを何十件も列挙せず、当該 `testCaseId` に対して `stepId: "*"` で 1 件に集約する**（一部ステップのみの場合は個別 `stepId` を指定）。共通理由と根拠は `reasons` に一度だけ定義し、各項目からは `reasonRef` で参照する。
   - **管理記録の終端更新**：当該 `executionId` の記録に対し、検証済みの参照索引（`result_ref`）、終端状態（全必須ステップの操作完了は `COMPLETED`、操作異常・前提不成立・保存失敗は `ERROR`、期限超過は `TIMEOUT`、中断指示は `ABORTED`）、および終了日時（`finished_at`）を同時に保存・回読する。
   - **返却サマリ**：実行 ID、対象範囲、全体の実行状態、実施した操作と結果の概要、完了・失敗・`notRun`・不明の件数、および証跡・参照索引の保存状態を簡潔なサマリとして返却する。
