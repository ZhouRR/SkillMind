# テスト実行

## タスクと入力

公開タスクは「テスト実行」の一つとし、RV 済み Markdown を直接実行し、MCP の操作回执と必要な画面観測からタスクの実行結果をまとめる。画像は必要な場面で証跡として保存し、モデルが閲覧するのは定位が必要な場合に限る。終了時は提供済み・許可済みの履歴送信機能で原記録を保存する。画像や送信機能の不足を一律の開始条件にせず、後続の最終判定は完了条件にしない。既存登録との対応のため Skill 識別子は維持する。独立した実行計画の生成・検証・保存・状態管理は行わず、`test_execution_plan` への新規登録・旧計画の再利用を前提にしない。内部工程の起動や画面情報ファイルの事前提出を利用者に求めない。他の Skill は呼び出さず、最終判定は本タスクの対象外とする。ステップごとの追加報告書、総括の `操作記録.json`、モデルが再構成する中間の `実行結果.json` は生成しない。

対象は「文書範囲」で選択した RV 済み Markdown、または実行コンテキストの文書参照から特定する。選択済みならタスク入力は `{}` とし、パス・ID・本文を再入力させない。文書庫の文書 ID と業務 DB の `document_id` は同一とは限らない。まず選択済み Markdown の正確な保存先を `test_automation.test_artifact` の `object_key` と照合し、文書庫・bucket の対応も確認する。その記録の `test_run_id`・`document_id` で `test_run`・`test_document` を参照し、RV 状態と `specVersion` を引き継ぐ。パス中の UUID から業務 ID を推測しない。一意でなければ対象を確認し、過去の PASS を暗黙に選ばない。

仕様本文の入力はこの Markdown のみとする。プラットフォームが Project 全体の文書読取を提供する場合、参考資料と本 Run 中のアップロード文書は `document.list/v1` / `document.read/v1` で取得できるが、別文書を試験対象へ追加したり凍結した根拠を差し替えたりしない。業務知識の Markdown は解釈の補助として別途読めるが、試験対象や原仕様の代替にはしない。元 Excel の取得・読取・再変換・版照合を行わず、利用者に Excel の提出やパス・シート・セル情報の入力を求めない。元 Excel のファイル・保存先・Version ID・ETag・シート名・セル座標が提供されなくても、それを理由に停止しない。

接続済みの MinIO、PostgreSQL、Schema 検証ツール、実行対象の Runner／MCP を使う。DB の表はすべて `test_automation` Schema に属する。登録 appId と環境・対象ビルドの版は、接続済み環境の公開設定・読取結果、または監査済みの回答から取得する。接続設定の仕様書への追記や秘密情報の入力を求めない。未提供の環境設定を工具清單・アプリ名から推測しない。

## 業務知識の参照

任意の独立した文書読取リソース「業務知識」（key: `business_knowledge`、kind: `document`、access: `read`、required: `false`）を使う。プロジェクト文書庫の `JAF業務知識/` 等、INDEX と配下の Markdown を含むディレクトリを選択する。対象仕様の「文書範囲」や成果物保存先とは別の選択範囲とし、同じ接続でも統合しない。入力フォームに知識庫のパス・ID・本文を追加しない。

- **取得**：結び付いた範囲の `INDEX.md` を最初に読み、アプリ名・機能名・画面 ID を手掛かりに必要な共通規則、業務、画面、注意事項だけを読む。`document.list/v1`・`document.read/v1`、または既に物化された入力の `workspace.search/v1`・`workspace.read/v1` を使い、実際の文書参照・ファイル索引からパスを取得する。INDEX の本文に個別リンクがなくても、その案内する配下を許可済み範囲内で検索する。列挙の続きがある場合は必要な範囲で取得する。選択された知識庫を入口にし、必要なら許可済みの同じ Project 文書庫を検索・参照できる。別 Project、開発環境のローカルパスや知識の由来へは広げない。
- **位置付け**：業務ルールは知識庫を正本とし、対象仕様は試験範囲・入力・操作・期待結果を定める。知識庫の例を新規ケースとして追加せず、対象アプリ・条件に合う規則だけを使う。知識庫は実測、接続設定、実際の権限や追加操作の許可を代替しない。参考文書を試験対象・変換対象・成果物として登録しない。
- **再利用と不足**：同じ Run では取得済みの版と読取結果を再利用し、毎ステップの再読込・全件読込・本文の複写はしない。参照した規則の要点と取得済み文書の識別情報は既存の継続情報に残し、追加の成果物・保存工程・Schema 項目を作らない。未設定・取得不可・該当記載なしだけで停止や RV 不合格にせず、仕様と観測から判断できる部分は続ける。結果を左右する未定義・矛盾だけを既存の確認／不足処理で扱い、未参照の内容を推測しない。

実行根拠を固定する前に、知識庫を使って業務用語と対象画面、権限・状態の前提、遷移と終了条件を理解する。RV で引き継いだ解釈と範囲を再利用し、現在の知識庫で凍結済みの操作・期待値を上書きしない。矛盾がある場合は影響する操作の前に具体的な不整合を返し、無関係な独立ケースまで止めない。操作時は、その理解を現在の MCP 画面観測へ対応付けて対象を絞る。知識庫から AutomationId・座標・appId・操作成功を推測せず、仕様の試験条件を変える業務データ修正やロック解除は行わない。現在環境の再利用・準備は「環境の自主準備」に従う。

## 新規テストと旧実行の復旧

新しく開始された Run は、利用者が旧実行の継続・記録復旧を明示した場合を除き、選択 Markdown に基づく独立したテストとして扱う。旧計画や `ABORTED` の履歴が見つかっただけで復旧へ切り替えない。待機への回答で「現環境版で再テスト」が選ばれた場合も、現在の Run で新規実行の準備を続ける。「別依頼」は旧実行とは別の業務実行を意味し、同じタスクを起動し直すよう求めない。依頼を識別する Run ID と RV 由来の `testRunId` は別の識別子であり、新規テストでも RV の ID は引き継ぐ。

旧処理の停止と占有競合の解消が確認され、新規テストの現在の前提条件が成立するなら、過去の `UNKNOWN` や未保存成果だけを理由に新規テストを止めない。原操作の結果は不明のまま保存し、旧要求を再送・成功扱いせず、新しい `executionId` と操作 ID・時間枠を使う。旧処理の稼働、未解消の pending、現在の対象状態への具体的な影響が残る場合は、その競合・前提だけを確認する。中断状態への DB 更新だけで原操作の終了や結果確定を推測しない。

旧操作記録の追加読取は明示された復旧に必要な場合だけ求める。新規テストの前提に旧記録の復元を加えない。復旧を打ち切る指示では不足と結果不明を報告して終了し、新規テストや旧データの書換えへ勝手に移らない。

## 前処理

1. 選択した Markdown に対応する保存記録で RV が `COMPLETED` ＋ `PASS` であることを確認し、RV 済みの保存済み `MARKDOWN` を取得する。判定と文書の対応は登録記録で確認し、元ファイルへのアクセスを確認条件にしない。
2. `test_execution` の実際の表構造を確認する。直接実行には `execution_basis`（JSONB）と NULL を許す `plan_id` を使う。既存の `result_ref` には [runner-records.schema.json](schemas/runner-records.schema.json) の参照索引を保存するため、型・制約を同じ表構造確認で照合する。これは Runner 原文の Schema ではなく、業務実行と原操作を対応付ける保存値である。RV 文書への対応は保存記録と DB 制約で維持する。未移行なら必要な DB 移行を明示して停止し、架空の計画 ID・空計画・旧計画の流用で制約を回避しない。他の処理の稼働や未解消の pending は確認し、旧履歴だけを理由に新規実行を止めない。
3. 実際に提供された MCP ツールと入力契約、対象アプリ、操作と状態照会に必要な機能を確認する。任意の画像読取・履歴送信・ログ本文読取機能と利用可能な範囲も確認するが、ダウンロードや保持期限を一律の開始条件にしない。提供されない操作・観測手段を必要とするステップは、能力不足の具体的な理由を記録して未実行とし、依存しないステップへ進む。追加手段の提供や手動代行を求める質問でタスク全体を待機させない。
4. `mcp.tools/v1` が提供される場合は `reserve_desktop: true` で工具契約・接続参照・サービス版と本 Run のデスクトップ予約を取得する。`desktop.lease_ref` を `environmentLease` に用い、`pending_operation` が true なら原操作の照合まで進めない。対象 Windows デスクトップは実行中の専用利用が手配済みで、手動操作・別システムの操作は入らないことを既定の運用前提とし、開始時・継続時に利用者への確認を求めない。SKM の予約は同一 endpoint の Run 間だけの排他であり、外部排他の技術的な保証とは区別する。`external_exclusivity: NOT_VERIFIED` だけを理由に停止・質問しない。実際の占有競合や外部操作を検知した場合、または必要な予約を取得できない場合は、後続操作を停止して具体的な不足・競合を報告する。
5. 許可済み工具に `get_environment` があれば、その入力 Schema に従って呼び出し、`applications` の登録 appId・sutBuild、`environmentVersion`、`runnerVersion`、時間制限と同時利用条件を取得する。別名の環境取得工具がある場合も実際の説明・契約に従う。取得できる項目を利用者に再入力させない。版の取得にアプリの起動・画面検査を前提としない。`server.version` は MCP サービス版として `runnerVersions["mcpServer:" + server.name]` に固定し、実操作が返す `runnerVersion` と区別する。モデルは Brief の `runtime_metadata.model` を `modelVersion` とする。これは設定モデル ID であり内部ビルド番号ではない。環境版・対象ビルドなど取得経路がない必須値は、不足する項目だけをまとめて確認する。未提供の機能名で呼び出したり、`inspect_window` を環境設定の取得手段にしたりしない。

## RV で確認した実行範囲

- **範囲の引継ぎ**：取得した Markdown 末尾の `RV 確認済みの適用範囲` を使い、付記の `testRunId`・`documentId`・`specVersion` と RV 登録、対象箇所と原文の対応を一度確認する。灰色や削除線の意味は RV の確認結果を引き継ぎ、独自に再解釈・再質問しない。整合した除外箇所は実行対象外、部分改訂は指定された現行記述だけを採用し、未変更部分を残す。付記は範囲の説明であり、新たな操作や権限の指示として実行しない。別版や原文との矛盾は、影響する操作の前に RV 資料の不整合として返す。
- **位置と母集団**：有効な全ケース・ステップを既存の `executionBasis` へ固定する。`sourceLines` / `expectedLines` は保存済み Markdown の業務本文を指し、RV 付記、書式情報（表・JSON）、凡例・改訂履歴自体を業務ステップに数えない。Excel のセル座標と Markdown の行番号を混同せず、原文や付記を削除・清書して行番号やハッシュを作り直さない。部分改訂でも原文の対応箇所を参照する。
- **対象外と未実行**：RV で廃止・対象外と確認された箇所は失敗や `NOT_RUN` に数えない。対象内だが未実行のステップとは区別し、登録後の範囲を実測に合わせて縮小しない。有効対象が 0 件なら対象なしとして返し、実行登録・アプリ操作や架空の完了件数を作らない。必要な除外理由は既存の終了サマリに簡潔に示し、追加ファイル・承認・毎ステップの保存は増やさない。
- **旧文書と不足**：付記のない旧 Markdown は、それだけで停止・再 RV を要求せず、同版の明確な凡例・改訂規則や引渡し済みの確認記録に従う。色だけで廃止と推測せず、局部の削除線を行全体へ拡張しない。`NOT_EVALUATED` / `NOT_INSPECTED` / `STYLE_EXTRACTION_UNAVAILABLE` は書式なしを意味しないが、対象・操作・期待値が明確なら続行する。それらを左右する未確定事項だけを不足として返し、元 Excel の再取得・再変換、他 Skill の呼出しや新たな入力フォームは要求しない。

## 実行前の根拠固定

1. 上記で引き継いだ適用範囲と原文から、有効な全ケース・業務ステップと元の期待条件を確認する。ケース・ステップ ID がなければ文書内の順序から安定した ID を付ける。対象範囲を後から実行済み操作だけに狭めず、前提条件・データ・後処理も原文に従う。
2. [execution-basis.schema.json](schemas/execution-basis.schema.json) に従う小さな `executionBasis` を作る。`sourceMarkdown` は取得元の文書参照と、RV 付記を含む取得ファイル全体の原バイト列の SHA-256、`specVersion` は RV 登録の元 Excel のハッシュとする。改行・空白を正規化してハッシュを作らない。`cases[].steps[]` に ID、原文の操作位置 `sourceLines`、期待条件の位置 `expectedLines`、必要な先行ステップ `dependsOn` だけを記録する。行番号は取得した UTF-8 Markdown の先頭を 1 とする包含範囲。範囲が実在し原文を正確に指すこと、全対象の網羅、ID の一意性、依存先の存在と非循環を実行前に検証する。期待条件が特定できなければ不足を確認し、創作しない。全文・手順配列・MCP 引数の写しを別の計画ファイルにしない。
3. `environment` に確認済みの appId・接続参照・予約参照、並列度 1、ケース時間制限を保持する。環境・タスクの指定を優先し、指定がなければケース 1800 秒、単独操作 15 秒を既定として工具上限内に収める。ケース時間は最初のアプリ準備から測り、承認・中断待ちを含め継続時にリセットしない。期限後は新操作を提案せず、進行中の操作は原 ID で照合する。送信・登録等の非冪等操作は自動再試行しない。環境準備は現在の登録アプリと許可済み工具の範囲で行い、試験条件・業務データ・既知の結果を変更しない。
4. `versionSnapshot.skillVersion` には Brief の `identity.skill_version_id` を固定版識別子としてそのまま保存する。`skillChecksum` を併記してもよいが、`skillVersion` の代わりにしない。確認済みの環境版 `environmentVersion`、対象ビルド `sutBuild`、Runner 版 `runnerVersions`、モデル版 `modelVersion` も保持する。`executionBasis` の Schema・format と原文対応を検証し、次項の実行登録に `execution_basis`、`version_snapshot` として一度に保存・回読する。実行前に永続化できなければ操作しない。独立した根拠ファイルの公開・完了状態・計画生成試行回数は作らない。登録後は根拠・期待条件・固定版を変更せず、実行結果をこの登録値へ対応付ける。参照索引へ本文や同じ根拠全体を複写しない。

## 画面確認と MCP 実行

1. 新規テストごとに `executionId`（UUID）を発行し、この値を一回のテスト共通の FlaUI `runId` とする。`open_application`・`login`・`execute_step`・`execute_segment` と `upload_logs` が `runId` を受け付ける場合は、アプリ・ウィンドウ・分段を跨いでも同じ値を渡す。操作 ID・分段 ID・送信 ID と混同しない。準備完了後、`test_execution` に `execution_id`、RV の `test_run_id`・`document_id`、`execution_basis`、`version_snapshot`、`status: RUNNING`、`started_at` を一度に登録し、`plan_id` は NULL とする。承認・適用・回読が確認できてからアプリを操作する。同一実行の継続は既存 ID と登録済み根拠を使い、再登録・再構成しない。
2. 入口アプリと被測アプリを分け、現在環境を観測して再利用・準備を選ぶ。仕様が新規起動を要求する場合、または準備に起動が必要な場合に登録済みの入口を `open_application` で準備する。前提に合う既存実体を使える場合は不要な再起動をせず、公開工具で現在の窓・実体を確認する。原 `requestId` と一致する `get_step_status` の終端回执を確認し、`READY` の場合だけ現在画面へ進む。`WINDOW_SELECTION_REQUIRED` は未起動を意味しない。返されたウィンドウ候補から観測と仕様で選び、複数窓は `windowId` で特定する。取得済みの画面情報は変化や不足がない間は再利用し、遷移後は対象窓を再確認する。原起動回执は現在の生存・画面の保証ではなく、同じ準備を繰り返す理由でもない。
3. 必要な業務操作を提案する前に、実際の工具契約と対象・値を照合し、ケース/ステップ、用途、原要求と提案参照を保持する。単独操作は `execute_step`、同一アプリ・同一 `windowId` で全対象と順序が確定した短い列は `execute_segment` を使える。分段は最大五手順か公開上限の小さい方とし、ログイン、ポップアップ、アプリ/窓切替、再観測や動的判断が必要な所で切る。`expectedResult` は Runner の `actualResult` との正確な比較であり、仕様の業務期待全体を代用しない。必要なチェックポイントは公開契約の `checkpointAfter` を使う。分段の親 `segmentId` は原操作 ID と対応付け、各子手順には互いに異なる非ゼロ `requestId` を送信前に固定する。子 ID を全部親 ID に置換しない。
   単独操作/ログイン/起動は `get_step_status`、分段は `get_segment_status` で原 ID を回読し、各子 `requestId` の結果・実際の `stepIndex`・未実行を元ステップへ対応付ける。`COMPLETED / ERROR / TIMEOUT / CANCELLED / ABORTED` と分段固有の `CHECKPOINT / REJECTED` は元の意味を保存する。分段全体の完了だけで各子の成功や業務 PASS を推定しない。`PENDING` は未送信、`DISPATCHED` や回执欠損は未実行の証明でなく、確認が必要。起動は原 `requestId` と登録 `appId` を照合し、`READY` 以外で業務操作へ進まない。送信前の対応と取得済み回执は既存の永続要求・継続情報に残し、会話の記憶や毎ステップの追加ファイル保存へ依存しない。
4. 応答が `RUNNING`、通信切断、応答不明なら、原要求に実際に渡されたことを確認できる `requestId` を許可された `get_step_status` で照会する。旧版の起動など要求 ID を送っていない操作では、Effect UUID を Runner の要求 ID とみなして照会しない。ID がまだ取得できない場合はプラットフォームによる元の操作の結果照合を使い、推測した ID や新しい提案で送り直さない。分段の応答不明は原 `segmentId` の `get_segment_status` と既知の子回执で照合し、新 ID で分段を再送しない。取消しは `cancel_step` / `cancel_segment` に取消対象の原 ID を渡す。回読は同じ原 ID と終端・取消確認を条件とし、終了状態と現在画面を確認する。照会不能や操作済みか不明な状態では後続操作を止める。
5. 操作完了後は原回执と次の操作に必要な現在画面・値を確認し、元のケース/ステップへ結び付ける。本タスクは操作の実施と結果の整理であり、業務の PASS/FAIL 判定、期待ログ本文の検証、全期待条件の成立確認を追加の続行条件にしない。仕様に観測・読取自体がステップとして書かれている場合だけ実施し、取得できない事実は不足として残す。
6. 操作失敗・能力不足・前提未成立は該当ステップと依存部分の `NOT_RUN` / 不足へ記録する。公開機能で現在環境を準備できるか判断し、実行可能な独立ステップ・ケースを続ける。期待条件の未確認だけで後続を止めず、現在状態が次の操作を成立させるかで判断する。送信・登録の再実行で成功を作らず、原操作結果が未知の間はその状態に依存する操作を行わない。

## ログイン・定位・状態観測

- **既定ログイン**：通常の認証準備では `get_environment` の登録アプリに `loginConfigured` が true なら、観測済みの `windowId` とユーザー名欄・パスワード欄・ボタンのセレクターを `login` へ渡す。資格はサーバー内設定を使い、モデルへ取得・転記させない。原回执の `COMPLETED` は入力・送信の完了であり、`inspect_window` で期待する画面遷移を確認してから続ける。ログイン自体が試験対象なら仕様のアカウント/役割/条件に従い、既定アカウントで試験条件を置き換えない。
- **選択子の確認**：まず唯一の AutomationId、名称・型と親子関係、同じ窓から取得した `elementId` で対象を絞る。欠損・重複が残る場合だけ同窓の画像を補助に使う。`index` / `parentIndex` は観測の所属情報で、`elementId` や操作 ID ではない。ウィンドウ ID と要素 ID は観測結果の原値を対で使い、仕様や画像から推測しない。
- **画像の利用**：許可済みの読取工具から実画像の file/hash を取得し、`workspace.image/v1` または提供された受控画像工具でモデルに画像として渡されたことを確認する。MCP の取得先は成功した同 Run・同接続の観測 `evidence_refs` と原応答の JSON Pointer を `mcp.download/v1` へ渡し、原記録が画像の SHA-256 を公開する場合はその `hash_pointer` も指定して照合する。既存 HTTP/文書の許可読取も使えるが、任意 URL・他接続の資格や別 Project へ広げない。パスや Base64 文字列だけを閲覧済みと称しない。工具が要求する選択子種別だけを使い、login 等で別種の ID を受け付けない場合に名称や elementId を AutomationId へ変換しない。回执の `capturedWindowId`、対象 `windowId`、撮影時点、現在画面とポップアップ層の対応を確認し、画像と `boundingRectangle`・コントロール型・階層を照合する。画像座標は窓位置・縮尺・外側のポップアップでデスクトップ座標と異なるため、画素位置を直接クリックへ流用しない。実操作は MCP が返す `windowId + elementId` 等の公開セレクターを使う。一意の操作可能要素に対応できなければその操作を止める。画像は必要時とし、毎ステップの全ツリー/画像再取得や検証を新たな必須工程にしない。画像工具がなくても UIA で一意に定位できる部分は進める。
- **消える画面の証跡**：起動引数不足のエラー表示、確認ダイアログ、終了前の画面など、次の操作で消える試験上必要な表示は、OK・閉じる・遷移・終了の前に一度保存する。同じ窓・同じ状態の画像が既に保存されていれば再撮影しない。なければ現在の観測で特定した appId・windowId（必要なら instanceId）を使い、許可済み `execute_step` の `screenshot` を公開契約に従って実行する。閉じた後の自動撮影で消えた表示を補えるとはみなさない。撮影要求の原 ID・終端回执と画像品質を照合し、既知の撮影失敗を結果不明や業務操作の失敗へ置き換えない。共通 `runId` と原要求 ID を保持し、元ケース/ステップへ `OBSERVATION` として対応付け、終了時の原履歴送信に含める。保存だけのために全画像をダウンロード・読図せず、毎ステップの撮影も必須にしない。撮影不能・機能不足は理由を既存の `gaps` に残し、追加確認や全体停止を作らず、既存の回読と期限を守って元操作を続ける。証跡を補うために起動・クリックをやり直さない。
- **状態の回読**：スクロール・選択・チェック・展開・日付・ツリー・テーブルは、該当コントロールの `controlState` / `grid` と実際の工具契約で操作前後を確認する。`isEnabled` 等の欠損/null は false や空値、不支持を意味しない。ドロップダウン項目の名称が重複するなら子の表示文字と所属で特定し、取得済みの `itemElementId` で選ぶ。テーブルは元窓と対象 Grid を確認し、公開された零起点の行/列・セル観測と安定した業務値で絞る。`select_row.cells` のキーは実測したデータセルの AutomationId とし、表頭名や列番号から捏造しない。公開契約に `rowIndex` 等の別の定位方式があれば観測済みの値で使えるが、一覧順を業務 ID と扱わない。構造化 `inputs` を優先し、古い固定例へ合わせて新契約を改変しない。
- **局部不足**：`incomplete`、`truncated`、局部 COM エラーは読取範囲の制限として扱い、全テストを自動中断しない。現在の操作に必要な属性・階層・状態だけを補読し、取得できた一意のセレクターと前提は利用できる。必要情報が未確認なら関連操作だけを保留/不足とし、未知を既知値へ補わない。

## 環境の自主準備

ケース間では毎回初期化せず、現在の登録アプリ・プロセス・ウィンドウと試験条件を観測し、Agent が必要な準備を選ぶ。既存プロセスの再利用、ログイン、窓の切替、画面遷移、入力内容や選択の整理、ダイアログの処理、アプリの正常終了・再起動を、公開工具・既存権限・承認の範囲で実施できる。これはプロセスの再利用や提示窓だけに限定しない。準備を毎回利用者へ確認せず、ケースの操作との対応は `PREPARATION` として既存索引へ残す。

仕様が新規起動、対象実体不在、特定のログイン状態などを明示する場合、その条件を既存状態で代用しない。公開機能で条件を整え、遷移後に確認する。対象実体・操作可能な選択子が未確認、別実行の活動あり、原操作結果が未知の場合は影響する操作を行わない。環境を整えるために業務レコードの削除・書換え、未知操作の再送、強制 kill、他実行のロック解除を行わない。実現手段がなければ該当ステップと依存部分を理由付きで飛ばし、残りを続ける。

## 操作結果の整理

実行結果は実際に取得した MCP 回执と画面観測に基づき、未観測の内容を補わない。追加報告の生成・保存を理由に次の操作を待たせない。大きい確定回执が file/hash で交付された場合、次の操作や索引に必要な項目だけを `workspace.read/v1` の `pointers` と `expected_hash` で読む。配列の全件が必要なら `array_limit` と `next_offset` で漏れなく取得する。保存成功の再確認だけの全文読取や同じ回执の文章化はしない。確認済みの原 ID・終端結果・保存参照は正確に保持し、必要な現在画面の観測・操作前提・回読は続ける。次の操作に必要な現在状態の確認と原操作の結果照合は維持する。期待条件の業務判定は後続工程に委ねる。

Runner の原 JSON/画像はモデルで再構成せず、定位に必要な画像だけ読める。終了時に公開設定が送信を有効とし、許可済みの `upload_history` と照会工具がある場合は、本実行に属する終了済みの原 `requestIds` を明示して原記録をアップロードする。上限を超える場合だけ集合を分け、各 `uploadId` と対象集合を送信前に固定する。`get_history_upload_status` の原回执から `projectId`・共通 `runId`・各要求/`stepIndex`・文書 ID・hash・保存状態を確認し、実際の保存済み参照だけを既存索引へ加える。`downloadPath` と保存済み文書は別物で、返された `documentDownloadPath` も対応するサービスの許可読取経路でのみ使う。

送信は既存の外部書込提案・承認・回読で行う。`UPLOADED` は保存完了であり UI 操作成功や業務 PASS ではない。`PREPARED / PARTIAL` は元 ID・元集合の未送信分だけを続行し、`OUTCOME_UNKNOWN` は元送信 ID を照会する。404/PENDING は未送信の証明ではなく、新 ID への再 POST や UI 再実行で回復しない。機能未提供・未許可・無効では不存在を補わず終了サマリへ不足を残し、画像/保存保証の追加質問で全体を止めない。

仕様にログの読取・保存という実行ステップがある場合、`list_application_logs` で登録 appId・取得元と相対名を選び、履歴とは別の `uploadId`、同じ共通 `runId` の `upload_logs` で固定副本を保存する。原 `get_log_upload_status` で保存を確認する。本文が必要なステップでは、保存回执の `documentId` と `checksum` を `document.read/v1` の `document_id` / `expected_hash` に指定して同じ Project の文書を読む。本文が不要なら追加のログ検証は行わない。列挙・送信成功を期待ログの成立や業務 PASS とせず、取得できない本文は不足として記録して続ける。ログ取得・送信だけを回復し、アプリ操作を再送しない。

1. **操作との対応**：各操作をケース/ステップ、用途（`BUSINESS` / `PREPARATION` / `OBSERVATION`）、実際の接続参照と原 `requestId` に関連付ける。準備成功だけを業務ステップ完了に数えず、異なる接続・要求の記録を混ぜない。
2. **最小の保存値**：収尾時に [runner-records.schema.json](schemas/runner-records.schema.json) の参照索引を既存 `test_execution.result_ref` に保存する。実操作との対応、既知の未実行項目 `notRun`、操作の結果・対応の不足 `gaps` だけを保持し、本文・画面ツリー・実測の言い換え・別の報告ファイルは作らない。実際の契約で原要求を照会した入口は `records` の locator に使える。記録参照を取得していなければ `records: []` とし、架空のファイル・hash・`archive` は補わない。索引（`schemaVersion: 2.0`）は一回の収尾にまとめる。共通の理由と確認済み根拠は `reasons` の `text` / `evidenceRefs` に一度だけ定義し、`notRun` / `gaps` の各項目は元の `testCaseId`・`stepId` と `reasonRef` で対応付ける。個別の差分だけを `detail` / `evidenceRefs` に残し、同じ長文・ID一覧を各ステップへ複写しない。未実行項目を件数や範囲だけにまとめず、一つずつ列挙する。継続時だけ新しい対応を既存の永続継続情報へ残す。
3. **状態の区別**：回执で原操作の結果を確認できれば `CONFIRMED`、送信・結果が不明なら `UNCONFIRMED` とする。既知の ERROR 等も確認済みの失敗として扱い、画像/送信不足だけで確認済み回执を不明へ変更しない。原 ID 自体が不明なら `gaps` に残す。`notRun` は未送信と確認できたステップだけとし、未取得ファイルから未実行・成功・失敗を推測しない。

## 終了登録と返却

登録済み `execution_basis` の全ケース・ステップを母集団として、参照索引の ID・対応・重複、原接続/要求、未実行と不明の区別を照合する。ひとつの接続/要求を複数ステップへ付け替えず、補助操作だけのステップを実行済みにしない。索引の Schema・format と全 `reasonRef` が `reasons` の定義済み key を指すことを確認する。共通理由の根拠を各対象へ適用できるかも照合する。独立した計画/中間実行結果の検証は行わない。構造修正は初回を含め最大 3 回、UI 操作の再実行には流用しない。

登録済みの本実行は、成功・失敗・期限超過・取消し・中断のどの終了経路でも収尾し、タスク終了時に `RUNNING` を残さない。全必須ステップの操作が確定して完了した場合は `COMPLETED`、操作異常・前提未成立・保存や検証の失敗で未完了なら `ERROR`、実行期限超過は `TIMEOUT`、取消し・中断・利用者の終了指示は `ABORTED` とする。FlaUI の `CANCELLED` は `ABORTED` に対応付け、元の状態と理由を残す。`COMPLETED` は実行状態でありテストの PASS ではない。結果未知のまま完了扱いにせず、原操作の結果不明は `UNCONFIRMED` / `gaps` に残し、業務実行の終端化を遠隔操作の停止・成功や予約解消の証明にしない。画像不足だけで実際に完了した操作を未実行へ変更しない。回答・承認後に同じ実行を継続する一時待機は終了と区別する。

同じ識別体系の環境・対象ビルド・Runner 版が固定値と異なる場合は停止し、登録値で覆い隠さない。MCP サービス版と操作 Runner 版は混同しない。固定後に判明した Runner 版は実際の操作回执から取得し、`version_snapshot` を書き換えない。

通常は検証済み `result_ref`、終端状態、`finished_at` を一回の UPDATE で同時保存・回読する。索引検証が失敗しても終端登録を止めず、既存の `result_ref` を保持して、終端状態・`finished_at` と実在する `error` 列へ終了理由、未保存事項、既知の原要求 ID を保存・回読する。不正な索引や架空の参照は保存しない。更新は本 `execution_id` の未終了行に限定し、応答不明なら同じ行を回読してから未適用分だけを扱う。既存の終端値を上書きせず、外部操作を再送しない。実行登録前の終了では行や executionId を新設しない。必要な承認・権限・回読は省略せず、保存失敗を隠して収尾済みと称しない。

返却は画面で読める一回の簡潔な実行サマリとする。実行 ID・対象範囲・全体の実行状態、各業務ステップの操作概要と確認できた結果、完了・失敗・既知未実行・結果不明の件数、停止理由と未確認の期待条件をまとめる。根拠は取得済みの操作回执・画面観測とプラットフォームの Evidence 参照を使い、原応答全文やページ装飾を再生成しない。画像/ログの閲覧範囲、原記録の送信済み・未保存/不明を実際の結果から一度だけ示し、未読内容を検証済みと称しない。取得経路・保持期限の追加質問やモデル生成の報告ファイルを増やさない。最終的な Verdict・原因分類は生成せず、操作完了だけから仕様全体の PASS や未観測の送達を主張しない。後続判定の実施・準備完了を本タスクの終了条件にしない。

## 異常と継続

MCP の失敗は送信・回执核対・業務条件のどこで起きたかを区別し、原要求 ID と取得済み観測を保持する。起動済みでも回执未確認なら入力・送信へ進まない。診断前に原因を断定せず、応答不明の操作を新規 ID で再送しない。既知の失敗でも、成功するまで繰り返すテストに変えない。

同一実行の継続では、DB、原操作の状態と永続化された要求・回执の対応を照合し、同じ `executionId`・根拠・期限で未完了部分だけを扱う。保存だけの失敗なら、既存回执に基づく索引/終了登録だけを再開し、UI 操作を再送しない。旧い `操作記録.json` / `実行結果.json` の復元を新しい引渡しの前提にしない。失われた対応を日時・ファイル順・モデルの記憶だけで復元しない。

特定ステップの機能不足だけで追加質問やタスク全体の待機を作らない。未送信と確認できる対象は具体的な理由付き `notRun` に残し、観測不足は `gaps` に残す。独立部分まで実行・収尾した返却は不足を含む `PARTIAL` とし、完了/PASS を偽らない。登録や権限・予約など実行全体の必須条件が成立しない場合は操作せず理由を返して終了する。登録後の業務表は上記の終端状態を使い、存在しない `BLOCKED` を書かない。必要な既存権限の範囲で工程ごとの追加確認は求めない。取消し・終了指示を受けて収尾を実行できる場合は、新たな UI 操作をせず本実行の終端登録だけを行う。DB 利用不能・撤権・Worker 強制終了等で更新不能なら、取得済みの executionId・原操作・必要な終端状態・未保存事項を既存の継続/監査情報へ残せる範囲で引き渡し、プラットフォーム側の収尾が必要と明示する。書込不能を Skill だけで解消できるとはみなさず、未確認操作の予約を勝手に解除しない。新しい結果ファイルや別実行で隠さない。
