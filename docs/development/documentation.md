# 文档维护约定

## 正本与派生内容

| 内容 | 放置位置 | 更新方式 |
| --- | --- | --- |
| 产品、术语、整体结构 | overview/ | 解释目的与组件关系，链接详细规则 |
| 不变量、协议语义、失败恢复 | design/ | 每个主题一个正本；标明现状与目标 |
| 当前状态、顺序和验收缺口 | planning/roadmap.md §13 | 实现/部署/专项验收分别举证 |
| 开发命令和变更指南 | development/ | 写明工作目录、依赖、输入和副作用 |
| 配备、backup、restore、故障处理 | operations/ | 根据操作风险给出前置和成功条件 |
| 业务质量标准 | acceptance/ | 说明样本、指标、数据隔离和人工判定 |
| 当时的实施记录 | history/ | 保留历史事实；新结论追加，不倒改旧报告 |
| 代码入口与 agent 约束 | PJM/*/README.md、AGENTS.md | README 做导航，AGENTS 约束变更 |
| Skill 输入与解释器指令 | PJM/skills/** | 可执行资产，遵守 version/hash/fixture 同步 |
| 浏览版 | docs/index.html | 从 Markdown 生成，不手改正文副本 |

Markdown 是可维护来源。浏览版只嵌入 docs Markdown、workspace/代码 README 和 AGENTS，不扫描 .env、内部配置、业务 Skill 原文、凭据、测试 Gold 或任意源码。

## 写一份设计

开头写用途、状态和前置文档；正文依次说明场景、数据/职责、成功与失败流程、兼容性、实施入口和验收。表格用于比较，短流程图用于表达分支，代码示例应能通过现有契约。

推荐使用以下骨架，可合并不适用的章节，不为了套模板制造空文档：

```text
标题：说明本页负责的一个主题
定位：设计/实现说明/操作指南；状态来源与前置阅读
1. 场景与非目标：为什么要做，明确不做什么
2. 决策与理由：规则、替代方案、取舍及受影响边界
3. 数据与职责：正本、调用方、冻结时点、现有 Schema/代码入口
4. 运行与失败：成功、拒绝、重试、幂等、并发、恢复
5. 兼容与实施：历史数据如何读取，哪些消费者需要同步
6. 验收：给定条件、操作、可观察结果、未覆盖范围
```

- 精确字段、enum 和 required 以 Schema 为准；示意结构明确标为目标或语义摘要。
- 已实现的功能提供实现入口。未实现的功能明确缺少的 API/Schema/页面，不写成用户操作步骤。
- “设计要求”“工作副本实现中”“已验证行为”分开写；若需要说明当前差距，标明核对时点并链接计划，代码文件存在不能替代链路测试。
- 发现设计与实现不符时分别写现状、影响、目标及同步范围，不能悄悄弱化设计或声称代码已修好。
- 不在 README、设计和计划同时维护同一进度表，不继续把实施日志追加到设计主文。
- 使用可点击的相对链接；旧 docs/01–13 略记由 [文档索引](../README.md#旧番号の対応) 解释。
- 保留有用历史，过时材料进入 history 并标注时点。归档不能成为当前功能或测试状态的证据。
- README/AGENTS 使用日文；设计正文沿用中文，协议与代码标识保持原样。
- 每页一个 H1，正文从 H2 开始；不从 H1 跳到 H3。新独立设计采用本页章节号，不继续使用从旧 PLAN 复制来的 26.x 等层级。

## 一次整理的更新顺序

1. 核对代码和契约，先向协作者说明冲突、影响面与本次是否修改实现。
2. 修改负责该规则的设计，再更新引用它的概览、操作指南与代码 README；不复制整段规则到所有入口。
3. 实现进度只更新 roadmap §13，旧章节与代码注释所用编号通过引用索引兼容。历史记录追加新结论，不覆盖旧时点。
4. 对照全部正式 Markdown 清单确认覆盖。Skill 的 SKILL.md/references 是执行资产，不因属于 Markdown 就移动或改写；变更时另走 version/hash/fixture 流程。
5. build、check、文档工具回归与相关契约检查后，再做浏览器人工可读性检查并记录实际范围。

代码目录新增 README 时同步工程入口。[script README](../../PJM/scripts/README.md)说明各工具的副作用；新加深层文档时明确更新 build 的 `source_paths()`，不要改成递归扫描所有源码、Skill 和配置。

## 生成和验证浏览版

以下在 `PJM/` 执行。依赖只用于文档工具，不改变 Backend/Web 运行依赖，也不需要虚拟环境。

```bash
python3 -m pip install --user -r scripts/docs-requirements.txt
python3 scripts/build_docs.py
python3 scripts/build_docs.py --check
python3 -m unittest discover -s scripts/tests -v
```

若 user site 不可写，可把依赖安装到工作区外明确的临时目录，并用 PYTHONPATH 指向它；不因此修改应用依赖或创建 venv。

build 检查 Markdown 标题层级、代码块、本地链接与章节锚点，并验证文档中带 `view_version` 的 ViewSpec JSON 示例。历史归档保留原有层级，不为新样式倒改旧正文。生成的 index.html 包含所有可浏览正文，可直接离线双击打开；不使用 CDN、运行时 fetch 或服务端。目录搜索支持标题和正文，历史默认单独折叠。

文档工具回归覆盖失效链接/锚点、代码块闭合、中文标题、离线导航、原始 HTML 不执行、嵌入范围与构建可复现性。它不需要启动应用或连接数据库。

`--check` 执行相同检查并比较生成物是否与来源一致，内容未同步时退出非零，不修改文件。变更 Markdown 或浏览模板后重新 build，再提交/交付来源与 index.html。

### 人工浏览检查

在桌面和窄屏各打开一次 `docs/index.html`：从产品页进入计划/设计/代码入口；搜索一个正文术语；跳转章节、刷新深链接并前进/后退；用键盘操作导航。桌面使用侧边章节目录，窄屏使用正文前的“本页内容”。

长表格和结构图允许各自横向滚动，但整页不能被撑出屏幕。实际溢出的表格显示滚动提示，键盘可聚焦滚动区域。历史页应有明显提示，默认搜索不混入旧结论。浏览器验证说明布局和导航可用，不代表 ProjectMind 应用页面已通过验收。

## 验证结果的表达
