# Jaf チケット分析 — 個別チケット入力&分析支援

> **最初に実行すること:** `/home/gradle/.claude/skills/jaf-quality-core/SKILL.md` を Read し、共通設定（用語定義、CF#一覧、接続情報、JAF規模一覧仕様、注意事項）をコンテキストに読み込むこと。

## バッチモード

引数に `--batch` が含まれる場合、以下のデフォルトで**非対話実行**する。
ユーザーへの質問は一切行わず、完了まで自動で処理する。

### バッチモード引数

| 引数 | 既定値 | 説明 |
|------|--------|------|
| `--source=csv` | csv | データソース。`csv` または `api` |
| `--svn=none` | none | SVN参照モード。`none` / `basic` / `deep` |
| `--output-dir` | (デフォルト) | レポート出力先ディレクトリ |

### バッチモードの自動化ルール

| ステップ | バッチモードの動作 |
|----------|------------------|
| Step 0-1 | `--source` 引数に従う。接続確認はスキップ（`connection_settings.json` をそのまま使用）。CSV選択時かつファイル不在時はエラー終了 |
| Step 0-2 | `--svn` 引数に従う |
| Step 0-3 | スキップ（`connection_settings.json` をそのまま使用） |
| Step 10 | スキップ（結果確認なしで次へ） |
| Step 11 | 常にレポート保存（`--output-dir` 指定時はそのディレクトリへ） |

### 使用例

```
/jaf-quality-ticket #1585 --batch --source=api --svn=deep
/jaf-quality-ticket #1607 --batch --svn=basic
```

#### 品質フィールド提案セクション（parse_report 互換）

`【品質フィールド提案】` は **2列Markdownテーブル** で出力する。このセクションは `##` で囲まず、`【品質フィールド提案】` 見出し行＋テーブルのみで構成する。

**厳守ルール:**
- テーブル形式: `| フィールド | 提案値 |` ヘッダー行 + 区切り行 + データ行
- フィールド名は `(CF#52)` などのサフィックスを付けず、Redmineのカスタムフィールド名と完全一致させる
- **原因機能名は Redmine の選択肢リストに存在する値を使用する**（JAF規模一覧の機能名をそのまま使わず、Redmine選択肢から最も近いものをbigram照合で選択）
- 原因アプリ・原因機能名・原因FID もこのテーブルに含める（JAF規模一覧から引き当て）
- **作り込み担当者（設計書／ＰＧ）の突合には、常に原因FIDを使用すること。検出時FIDはバグが顕在化した箇所であり、作り込み箇所とは異なる場合があるため、誤って検出時FIDで引き当てないこと。**
- 値には注釈（` — 妥当`, `後述`, `要記入`）を含めず、提案値のみを記述
- 記入済みで提案不要のフィールドは出力しない

#### 長文セクション（parse_report 互換）

`【根本原因内容】` と `【対応内容・回答内容】` はコードブロック（```）を使わず、本文をそのまま記述する。
サブセクションには `###` 見出しを使用する（`### 工程別の見落し原因` `### 根本原因`）。
セクションの前には `---` 区切り線を入れる。

**厳守ルール:**
- コードブロック（```）は使用しない
- セクション見出しは `【根本原因内容】` `【対応内容・回答内容】`（`（提案）` サフィックスなし）
- サブセクションには `###` 見出しを使用可能

#### 表示用セクション（parse_report 非対象）

基本情報・問題概要・参考情報は `##` 見出し + Markdownテーブル/リストで整形する。

| セクション | 見出し | 内容形式 |
|-----------|--------|---------|
| タイトル | `# Jaf 品質分析レポート — チケット #<番号>` | メタデータ行（分析日/作成者/モード） |
| 基本情報 | `## 基本情報` | 2列Markdownテーブル |
| 問題概要 | `## 問題概要` | `>` 引用 + 症状テーブル |
| SVN調査 | `## 参考: SVNソースコード調査結果` | 箇条書き + コードブロック |
| 設計書 | `## 参考: 設計書確認結果` | 箇条書き |
| 規模一覧 | `## 参考: JAF規模一覧 突合結果` | 箇条書き |

### 情報収集フェーズ

#### Step 1: チケット情報の取得

チケット番号が指定されていない場合は、ユーザーに番号を尋ねる。

**Step 0-1 で「1. Redmine API」を選択した場合 → 1a を実行する。**

**Step 0-1 で「2. CSV」を選択した場合 → 1b を実行する。**

##### 1a. API 経由で取得（推奨）

Step 0-1 で確認した URL と API Key を使ってチケットを取得する：

```bash
curl -s "<redmine_url>/issues/<issue_no>.json" \
  -H "X-Redmine-API-Key: <api_key>"
```

API レスポンスの `issue.custom_fields[]` から品質フィールドを抽出する。

#### 1b. CSV 経由で取得（フォールバック）

```bash
python3 /home/gradle/.claude/skills/jaf-quality-core/scripts/parse_issue.py /workspace/data/issues.csv <issue_no>
```

stdout には人間が読みやすいフォーマット、stderr には JSON 形式の構造化データが出力される。

#### Step 2: カスタムフィールド値の解決（API 使用時のみ）

API レスポンスでは、`enumeration_cf` タイプのカスタムフィールド値が数値 ID で返る。
`/workspace/config/jaf_redmine_field_mappings.json` を参照して ID→ラベル変換を行う。

変換が必要なフィールドと不要なフィールド：
- **変換必要 (enumeration_cf)**: 障害区分(152), 検出工程(143), 検出時環境(144), 再現性(174), 回避策(176)
- **変換不要 (list_cf)**: バグ区分(52) — 文字列値が直接返る
- **変換不要 (テキスト)**: 詳細内容, 原因内容, 根本原因内容, 題名 など

マッピングにない ID 値が出現した場合はユーザーに報告し、edit form の HTML から特定を依頼する。

#### Step 3: 基本情報の提示

出力を基に、以下の情報をユーザーにわかりやすく整理して提示する：

1. **基本情報**：番号、状態、優先度、検出日、検出時アプリ、検出時機能名、トラッカー、担当者、画面/バッチ/帳票/サービスID など
2. **詳細内容**：問題の前提条件、操作手順、発生内容、期待結果
3. **既に記入済みの品質フィールド**：どの列にどんな値が入っているか
4. **未記入の品質フィールド**：これから埋めるべき列の一覧

#### Step 4: SVN ソースコード参照（Step 0-2 で Y（基本/深掘り）の場合は必須）

Step 0-2 で Y（基本/深掘り）を選択した場合、このステップは**スキップ不可**。必ず SVN に接続してソースコードを実確認すること。

##### ソースファイル特定の優先順位

修正前後のソースレビューや Diff 確認が必要な場合、以下の優先順位で対象ソースファイルを特定する：

1. **最優先**: `修正プログラム1〜3`（CF#162-164）— チケットに記入された修正対象ファイル名
2. **次点**: `対応内容・回答内容`（CF#97）— クラス名・メソッド名・ファイルパスの記載を参照
3. **フォールバック**: 原因FID（CF#185）/ 検出時FID（CF#147）を手がかりに SVN を検索し、`検出時アプリ` の SVN パス配下から該当ソースを特定
4. **最終手段**: SVN コミットログ — チケットの記入に抜け漏れがある場合、`検出時アプリ` の SVN パス配下で `svn log` を取得し、コミットコメントから該当チケット番号・関連キーワードを検索して修正ファイルを特定する（[4d. SVNコミットログ検索](#4d-svnコミットログ検索) 参照）

> いずれの方法でも特定できない場合は、ユーザーに対象ファイルの指定を依頼すること。

**Step 0-2 で深掘りを選択した場合の追加処理:**
- ソースコードの該当箇所を特定し、不具合の原因となっているロジックを分析する
- 修正案（修正前後のコード差分）を提案する
- 特定した修正ファイル名を `修正プログラム1〜3` の候補として提示する
- **設計書の確認**: 原因工程が未記入で、不具合の原因が設計由来か実装由来かをソースコードだけでは判断できない場合、関連設計書も SVN から取得し、仕様記載の有無を確認する
- **重要:** 修正案は提案のみで、SVN への commit は絶対に行わないこと
- **テンプレート補完**: 深掘りで修正候補ファイルを特定した場合、以下のフィールドが未記入またはテンプレートのみであれば、深掘り結果に基づいて補完する:
  - `対応内容・回答内容`（CF#97）: クラス名、メソッド名、修正前のコード/動作、修正後のコード/動作 の形式で記述
  - `根本原因内容`（CF#158）: 【工程別の見落し原因】に各工程での見落し理由を、【根本原因】に真因を記述

##### 4a. アプリ名→SVNパス変換

`検出時アプリ`（CF#145）からSVNパスを特定する。対応表は [jaf-quality-core のアプリ一覧](/home/gradle/.claude/skills/jaf-quality-core/SKILL.md) の `SVNパス` 列を参照。

##### 4b. SVN内のソースファイル検索

```bash
svn list -R "<repo_root>/src/trunk/<app_path>" \
  --non-interactive --no-auth-cache \
  --trust-server-cert-failures=unknown-ca,cn-mismatch \
  --username <user> --password '<password>' 2>&1 | grep -i "<class_or_file_name>"
```

##### 4c. ソースコードの該当箇所確認

`svn cat` でファイル内容を取得し、修正前後の該当メソッドやロジックを確認する。

```bash
svn cat "<repo_root>/src/trunk/<app_path>/<file_path>" \
  --non-interactive --no-auth-cache \
  --trust-server-cert-failures=unknown-ca,cn-mismatch \
  --username <user> --password '<password>'
```

##### 4d. SVNコミットログ検索

`修正プログラム1〜3` が未記入で、`対応内容・回答内容` にもファイル情報がない場合、SVN コミットログから修正ファイルを特定する。チケット番号や機能名をコミットコメントに含むコミットを検索する。

```bash
# アプリのSVNパス配下で直近N件のコミットログを取得し、チケット番号で絞り込む
svn log --limit 50 -v "<repo_root>/src/trunk/<app_path>" \
  --non-interactive --no-auth-cache \
  --trust-server-cert-failures=unknown-ca,cn-mismatch \
  --username <user> --password '<password>' 2>&1 | grep -B1 -A3 "<ticket_no>\|<keyword>"

# 特定ファイルのコミットログ確認
svn log --limit 10 "<repo_root>/src/trunk/<app_path>/<file_path>" \
  --non-interactive --no-auth-cache \
  --trust-server-cert-failures=unknown-ca,cn-mismatch \
  --username <user> --password '<password>'
```

> `-v` オプションで変更ファイル一覧も表示されるため、チケット番号や関連キーワード（機能名、クラス名など）で grep して修正ファイルを特定する。

**注意:** SVN 接続情報（URL、ユーザー名、パスワード）は jaf-quality-core の「SVN 接続情報」セクションを参照。SSL証明書エラーが発生する場合は `--trust-server-cert-failures=unknown-ca,cn-mismatch` でスキップする（社内環境のため許容）。

#### Step 5: 設計書確認（Step 0-2 で Y（基本/深掘り）の場合は必須）

**Step 0-2 で Y（基本/深掘り）の場合:** このステップは**スキップ不可**。原因工程が既に記入済みでも、設計書の記載内容をSVNから実確認して整合性を検証すること。

- 原因工程が設計系（基本設計/機能設計/詳細設計）→ 該当工程の設計書を確認し、仕様記載の有無・正誤を検証
- 原因工程が製造 → 詳細設計書を確認し、正しい仕様が記載されていたか検証
- 原因工程が未記入 → 設計書の記載有無から原因工程を判断（必須）

**SVN検索スキップ条件:** 原因工程が製造工程以降（製造/単体試験/業務内結合試験/AP/PF内結合試験/システム内結合試験/システム外結合試験/総合試験/運用試験/環境）かつ `修正ドキュメント1〜3`（CF#159-161）がすべて未記入の場合、設計書の SVN 検索は不要。原因工程が製造以降で修正ドキュメント未記入ということは、純粋なコーディングミスであり設計書の修正を伴わないため。

**Step 0-2 で N（SVN参照なし）の場合:**
- `修正ドキュメント1〜3`（CF#159-161）に設計書ファイル名が記入されていれば、その情報を分析に使用する
- 設計書の実内容確認が必要な場合はユーザーに提供を依頼する
- いずれも不可の場合は「SVN未参照のため設計書確認未了」と明記する

##### 5d. 設計書の記載内容に基づく判断

| # | 必須セクション | チェック内容 |
|---|-------------|------------|
| 1 | 【工程別の見落し原因】 | ラベルの後ろに実質的な記述（5文字以上）があるか |
| 2 | 【根本原因】 | ラベルの後ろに実質的な記述（5文字以上）があるか |

チェック方法：
1. 根本原因内容のテキストから `【工程別の見落し原因】` と `【根本原因】` の各セクションを正規表現で抽出する
2. 各セクションのラベル除去後の実質文字数が 5 文字未満の場合、不足と判定する
3. どちらか一方でも不足している場合は不整合、根本原因内容が完全に未記入の場合も不整合とする

> **緩和条件:** `【根本原因】` セクションのみでも、原因工程の特定・各工程の見落し分析・真因の深掘りがすべて完結している場合は軽微不備扱いとし、`【工程別の見落し原因】` の追記を推奨するにとどめる。逆に `【工程別の見落し原因】` のみで `【根本原因】` が欠落している場合は不整合とする（真因の深掘りがないため）。

#### ⑩ 詳細内容・根本原因内容・対応内容のテンプレート文言チェック

##### 根本原因内容のチェック

以下のテンプレート文言のみが記入されているケースを検出する：

| テンプレートパターン | 判定 |
|-------------------|------|
| `【工程別の見落し原因】\n\n【根本原因】` （または類似の見出しのみ） | **テンプレートのみ** → 未記入扱い |
| `【前置き】\n\n【見落とし原因】\n\n【根本原因】` （または類似の見出しのみ） | **テンプレートのみ** → 未記入扱い |

判定基準：
- 見出しラベルの後ろに実質的な文章（20文字以上）が記述されているかで判定する
- ラベルを除去した後の実質文字数が 50 文字未満の場合、**テンプレートのみ**と判定する

##### 対応内容・回答内容のチェック

以下のテンプレート文言のみが記入されているケースを検出する：

| テンプレートパターン | 判定 |
|-------------------|------|
| `【直接対応内容】\n\n【根本原因対策・結果】` （または類似の見出しのみ） | **テンプレートのみ** → 未記入扱い |

判定基準：
- 「クラス名」「メソッド名」「修正前」「修正後」のうち 2 項目以上に実質的な記述があるか確認する
- 0〜1 項目しか埋まっていない場合、**テンプレートのみ**と判定する

##### テンプレートのみ検出時の対応

1. 該当フィールドを「未記入」として扱い、分析結果の記入率に反映する
2. ユーザーに「テンプレート文言のみで実質的内容が未記入」であることを指摘する
3. 分析を続行できるか判断し、困難な場合はユーザーに内容の記入を依頼する

> **注意:** 一括登録されたチケットは、全件が同じテンプレート状態で作成されていることが多い。
> その場合、個別チケットの品質分析（Step 9）に進む前に、まず詳細内容・根本原因内容・対応内容の記入を促すこと。
> テンプレート文言チェックの詳細は [jaf-quality-core の注意事項](/home/gradle/.claude/skills/jaf-quality-core/SKILL.md) も参照。

#### 矛盾検出時の対応

矛盾が検出された場合は：

1. 矛盾の内容を具体的に指摘する（どのフィールドとどのフィールドがなぜ矛盾するか）
2. 根本原因内容・原因内容などの**事実情報**から最も妥当な値を判断する
3. 修正案を表形式で提示し、ユーザーに確認する
4. ユーザーの合意を得た上で、以降の分析（未記入フィールドの推定）では修正後の値を使用する

#### Step 8.5: 記入済みフィールドの妥当性チェック

Step 8 がフィールド**間**の論理的矛盾を検出するのに対し、本ステップでは各フィールドの値が**事実情報**（詳細内容・原因内容・題名・JAF規模一覧・SVN実コード）と照らして正しいかを個別に検証する。

> **最重要: 原因内容・根本原因内容・対応内容の3項目は、記入済みであっても必ず設計書および改修前後ソースの Diff と突合すること。** 検証なしに「記入済み＝妥当」と判断しない。検証方法の詳細は [jaf-quality-core の注意事項](/home/gradle/.claude/skills/jaf-quality-core/SKILL.md) の「3項目検証ルール」を参照。

##### ⑨ 対応内容・回答内容（CF#97）の妥当性

| 情報源 | 検証内容 |
|--------|---------|
| 原因工程 | 設計系なら設計書修正の言及があるか、製造系ならコード修正の言及があるか |
| SVNソースコード（Step 4 結果） | 修正ファイル名・クラス名が実在するか |
| SVN Diff（Step 4/6 結果） | 対応内容の「追加」「削除」等の記述がSVN Diffの実体と一致するか |

- 「処理を**追加**」「実装されていなかった」とあるのに、SVN Diffで同一コードの**移設/移動**が確認された → ❌
- 「**削除**」とあるのに、削除されたコードが別メソッドに**移設**されていた → ❌

修正種別の使い分け：
- **追加**: 新規にコードが発生した場合
- **削除**: コードが完全に除去された場合
- **移設/移動**: 既存コードの実行位置・トリガーを変更した場合（削除+追加に見えても実体は移動）

| 情報源 | 検証内容 |
|--------|---------|

| 対応内容 | 修正内容と修正成果物の記述が一致するか |

| 情報源 | 検証内容 |
|--------|---------|
| SVN設計書（Step 5 結果） | 「設計書に記載されていなかった」が事実か |
| SVNソースコード（Step 4 結果） | 「実装されていなかった」が事実か |

- 原因内容/根本原因内容に「設計書に**記載されていなかった**」とあるのに、SVN設計書に当該処理の記載が確認された → ❌
- 原因内容/根本原因内容に「**実装されていなかった**」とあるのに、SVN修正前コードに当該処理が存在した → ❌

この場合の真の原因は「記載/実装の**有無**」ではなく「実行**タイミング/トリガー**の定義誤り」である可能性が高い。
例: 処理は設計書に明記され実装もされていたが、呼び出し元メソッド（トリガー）が誤っていた。

#### Step 9: 品質フィールドの分析と提案

以下の情報源を総合的に分析し、未記入フィールドの値を提案する：

- 詳細内容（問題の前提条件・操作手順・発生内容・期待結果）
- 既に記入済みの品質フィールド（参考情報として）
- 直近コメント（レビュー指摘など）
- ユーザーから提供された修正コードや変更内容

#### 各フィールドの分析基準

**障害区分（列 82 / CF#152）**
問題の発生形態を以下の 12 区分から選択する。全選択肢とIDの対応は `jaf_redmine_field_mappings.json` の `custom_fields.152` を参照。

| # | 障害区分 | 典型的な症状 |
|---|---------|------------|
| 1 | 表示内容不正 | 画面や帳票の表示値が期待と異なる |
| 2 | 画面動作不正 | ボタン押下・画面遷移など画面の動作が期待と異なる |
| 3 | 印刷内容不正 | 帳票・印刷物の内容が期待と異なる |
| 4 | 実行時エラー | 操作中にエラーダイアログや例外が発生する |
| 5 | プログラム異常終了 | アプリケーションが強制終了する |
| 6 | 操作続行不能 | エラーやロックにより操作を続行できない |
| 7 | 通信エラー | 外部システムとの通信が失敗する |
| 8 | 終了せず | アプリケーションが終了できない |
| 9 | システムダウン | サーバやシステム全体が停止する |
| 10 | ファイル/DB異常 | ファイルやDBのデータが破損・不整合 |
| 11 | ファイル/DBアクセスエラー | ファイルやDBにアクセスできない |
| 12 | その他 | 上記いずれにも該当しない |

**原因工程（列 91 / CF#54）**

> ナレッジベース更新の制約は [jaf-quality-core の注意事項](/home/gradle/.claude/skills/jaf-quality-core/SKILL.md) も参照。
