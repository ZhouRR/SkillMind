# Jaf プロジェクト品質分析 — 共通設定

> **最初に実行すること:** `/home/gradle/.claude/skills/jaf-quality-core/common.md` を Read し、JAF 全 Skill 共通の規約・パス・技術スタック情報をコンテキストに読み込むこと。このファイルは SKILL.md より先に読む必要がある。

以下のデータソースを組み合わせて多角的な品質分析を行う：

- **Redmine チケット**: issues.csv（CSVエクスポート）または REST API（リアルタイム取得）
- **レビュー指摘**: 詳設レビュー指摘一覧 / 製造レビュー指摘一覧（カラム定義は `config/csv_schemas.json` 参照）
- **単テ障害**: 単体テスト障害一覧（カラム定義は `config/csv_schemas.json` 参照）
- **規模・担当者**: JAF規模一覧.csv（約750機能、22列定義は後述）
- **品質基準**: JAF工程別品質目標.csv（原因工程×摘出工程の基準値）

> 全ディレクトリ構造は `config/data_directory.json` を参照。選択肢一覧は原則 `config/jaf_redmine_field_mappings.json` を参照。

## 用語定義

> **「新規バグ」の定義:**
> - **レビューCSV（詳設・製造）・単テ障害CSV での「新規バグ」:** 各CSVの `バグ区分` 列の値。指摘/障害のうち新規に発見されたバグを指す（非バグ/QA/重複/要望・仕変と区別）。
> - **Redmine チケットでの「バグ区分＝新規バグ」:** CF#52 の `バグ（新RS新規機能）` `バグ（現行改良機能）` `バグ（現行継承機能）` の3区分を合算したものを指す。APバグ以外/課題/仕変/コメント/重複/バグではない は除外。
> - 分析時に「新規バグのみ」と表記した場合、上記のフィルタ条件を適用する。

**用途:** 不具合チケットと突合して `詳設担当` `製造担当` `単テ担当` を特定可能。
`作り込み担当者（設計書）` には常に `詳設担当` を、`作り込み担当者（ＰＧ）` には常に `製造担当` を記入する。原因工程に関係なく**両方必須**。
担当者調査時は Redmine より JAF規模一覧.csv を優先する（より正確な担当者情報を持つため）。

**作り込み担当者の突合FID（最重要）:** 作り込み担当者の突合には**常に原因FID（バグを作り込んだ機能ID＝修正プログラムの属する機能ID）を使用する**。検出時FID（CF#147）はあくまでバグが顕在化した箇所であり、作り込み箇所とは異なる場合がある（例: 検出時FID=JAFRSHO07010、原因FID=JAFRSHS99000 業務共通機能）。修正プログラムから原因FIDを特定し、JAF規模一覧.csv の該当行から `詳設担当` `製造担当` を引き当てること。

**アプリ分類の基準:** JAF規模一覧.csv の `アプリ` 列はアプリ分類の正とする。レビューCSV（`詳設レビュー指摘一覧.csv` `製造レビュー指摘一覧.csv`）の `検出時機能 システム名` 列は JAF規模一覧.csv の `アプリ` 列と一致しない場合があるため、アプリ単位の集計では JAF規模一覧.csv の分類を使用すること。

**チケットとの突合ルール（最重要）:**
`検出時 画面ID/バッチID/帳票ID/サービスID`（CF#147）を**最優先キー**として JAF規模一覧.csv の `機能ID` 列と突合する。issues.csv の `検出時機能名` は「車業：ログイン機能」のような略称で記録されていることが多く、機能名でのマッチング率が大幅に低下するため、必ず以下の優先順位で突合すること：

1. **最優先**: `検出時 画面ID/バッチID/帳票ID/サービスID` ↔ `機能ID`（JAFRS* 形式、完全一致）
2. **次点**: `検出時 画面ID/バッチID/帳票ID/サービスID` ↔ `機能ID`（部分一致）
3. **フォールバック**: `検出時機能名` ↔ `機能名`（部分一致）
4. **最終手段**: 題名から JAFRS* 形式の機能IDを正規表現抽出して `機能ID` と突合

この優先順位を守ることで、マッチング率が大幅に向上する（機能名のみでは 30% 程度に対し、画面ID優先では 100% 近くになる）。

**単テ障害一覧との突合ルール:**
`単テ障害一覧.csv` の `機能ID` 列には、イベントID（`JAFRSAO02001E001` のような `E*`/`P*` サフィックス付き）が含まれる場合がある。JAF規模一覧.csv の `機能ID` は12桁のため、**先頭12桁で突合**すること。

```
単テ障害一覧.機能ID[:12] ↔ JAF規模一覧.機能ID
```

例: `JAFRSAO02001E001` → 先頭12桁 `JAFRSAO02001` で突合 → JAF規模一覧の `JAFRSAO02001` に一致

## 注意事項（全スキル共通）

- **詳細内容・根本原因内容・対応内容が「記入済み」に見えても、テンプレート文言のみで実質空欄のケースがある。** 記入率を報告する前に必ずテンプレート文言チェックを実施し、実質的な記入の有無を確認すること
- 分析は客観的事実（詳細内容、コード変更内容、既存の記入項目）に基づいて行う
- 推測で埋められない項目は「要確認」とし、ユーザーに判断を仰ぐ
- **原因区分（列 49）は分析対象外。** 原因区分_AI（列 88）を優先して使用し、原因区分の未記入は指摘しない
- 日本語の品質フィールドは日本語で記述する
- 参考になる既存チケット（特に #210, #211 など分析済みのもの）があれば、記述スタイルを統一する
- **CSV ファイルを直接編集しない。** 分析結果はレポートとして出力し、ユーザーが手動で CSV に転記する
- 分析に行き詰まった場合は、ユーザーに追加情報（修正コード、設計書の内容など）を求める
- **可能な場合は必ず SVN 上のソースコード・設計書を参照し、事実に基づいた分析を行う。** 推測のみの分析は避ける。
- **原因内容・根本原因内容・対応内容の3項目は、記入済みであっても必ず設計書および改修前後のソースコードと突合し、記述の妥当性を検証すること。** 記入済みでも事実と異なるケースがある（例: 「処理がなかった」と書かれているが実際は存在した、「追加した」と書かれているが実際は移設だった、「設計書に記載がなかった」と書かれているが実際は記載されていた）。不備を発見した場合は理由と修正案を提示すること。
  - **SVN 参照あり**: SVN 上のソースコード・設計書で直接検証する。スキップ不可。
  - **SVN 参照なし**: 以下の代替手段で検証を試みる。いずれも不可の場合は「SVN未参照のため検証未了」と明記する。
    1. `対応内容・回答内容`（CF#97）に十分な修正コード（修正前後のコードブロック）が記入されていれば、それを使用して検証する
    2. 不十分な場合はユーザーに修正コード・設計書の内容提供を依頼する
- **原因工程の判断が設計書の記載有無に依存する場合は、必ず設計書を確認してから判断する。** 確認できない場合は二案を併記し、ユーザーに設計書確認を促す（二案併記ルール）。
- **ナレッジベースの更新は自動では行わない。** ユーザーから明示的に指示があった場合のみ更新する。
- **チケットとJAF規模一覧.csvの突合ルール（CF#147最優先）は [JAF規模一覧.csv セクション](#jaf規模一覧csv22列カンマ区切り) を参照。** このルールは全分析モードで共通。
